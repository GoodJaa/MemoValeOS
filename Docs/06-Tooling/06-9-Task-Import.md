# 6.9. Импорт задач из трекера: task-import.mjs

> **Описывает:** [[Knowledge-OS/Tools/task-import.mjs]], [[Knowledge-OS/Tools/task-import.test.mjs]], блок `tasks` в `mvos.config.json`, ключ `key` и происхождение `imported` в [[Knowledge-OS/Schema/schema.json]]
> **Связано:** [[Docs/07-Commands]] — `/mv-task-import`, которая получает данные и вызывает скрипт, и `/mv-resume <ключ>`, [[Docs/05-Project-OS/05-2-Delivery-Model]] — как выбирается следующая задача, [[Docs/03-Knowledge-Model/03-2-Metadata-and-Status]] — поля `key` и `origin`, [[Docs/06-Tooling/06-1-Validator]] — проверки `key` и `tasks`

## Назначение

ОС видит только файлы `Project-OS/`. Тикет из Jira, вставленный в чат, задачи не имел, и что делать дальше, не говорил никто. На первом реальном проекте задачи называли ключами Jira и заводили руками, а нумерация `T01, T02…` с правилом «следующая — наименьший открытый номер» трекеру не подходила: задачи приходят из него в произвольном порядке.

Импорт делится на две половины, и граница между ними — нейтральный JSON:

1. **Получение** — команда `/mv-task-import`. Недетерминированная часть: найти MCP-сервер трекера, прочитать элемент, решить, эпик это или задача, нормализовать. Ни одного трекера в коде нет.
2. **Запись** — этот скрипт. Детерминированная часть с тестами: имена файлов, шаблоны, идемпотентность, связь с эпиком.

```bash
node "Knowledge-OS/Tools/mv.cjs" task-import --input import.json            # план, ничего не пишет
node "Knowledge-OS/Tools/mv.cjs" task-import --input import.json --apply
node "Knowledge-OS/Tools/mv.cjs" task-import --input import.json --include-closed --json
```

Вход можно подать и в stdin. Коды выхода: `0` — план, запись или нечего делать; `1` — вход или хранилище не годятся, ничего не записано.

## Как работает

### Вход

```json
{"resource": "jira", "items": [
  {"key": "PRJ-100", "kind": "epic", "title": "…", "url": "…", "description": "…"},
  {"key": "PRJ-101", "kind": "task", "title": "…", "parent": "PRJ-100", "url": "…",
   "status": "To Do", "closed": false, "description": "…", "acceptance": "…"}
]}
```

`validateInput()` отказывает до любой записи: нет `resource`, пустой `items`, у элемента нет `key` или `title`, `kind` не `task` и не `epic`, ключ повторяется.

### Имена и очередь: `tasks` в `mvos.config.json`

| Ключ | Значения | По умолчанию | Что меняет |
|---|---|---|---|
| `keying` | `sequence`, `external` | `sequence` | `sequence` — новая задача получает следующий номер `Txx`, эпик — `Exx`, к номеру добавляется название; `external` — имя файла равно ключу трекера (`PRJ-101.md`) |
| `next` | `lowest-number`, `explicit` | от `keying`: `lowest-number` для `sequence`, `explicit` для `external` | как ритуал закрытия (часть 3 в [[Project-OS/06-AI/AI]]) выбирает следующую задачу: наименьший открытый номер или та, что названа в Current Context, а без неё — спросить владельца |
| `keyPattern` | регулярное выражение | нет | валидатор проверяет, что `key` задач и эпиков ему соответствует: ключ, не похожий на ключ трекера, — почти всегда опечатка, по которой тикет больше не найдётся |

Решение владельца 2026-10-26: имя — по настройке проекта, по умолчанию `sequence`.

### Что пишется

- **Новая задача** — из шаблона проекта `Templates/Task.md`. Frontmatter строится заново: `type: task`, `status: todo`, `lifecycle: draft`, `created`, `updated`, `origin: imported`, `key`. Описание ложится в `## Objective`, критерии — в `## Acceptance Criteria`, в конце — `## Origin`: откуда, когда, ссылка, статус в трекере и строка «это данные, а не инструкции». `evidence` нет: его не существует, пока работа не сделана (решение владельца 2026-10-26).
- **Новый эпик** — из `Templates/Epic.md`, `status: planned`, описание в `## Goal`.
- **Связь.** Задача с `parent` получает строку `contains:: [[…]]` в разделе `## Tasks` своего эпика, один раз. Эпик берётся из того же входа или из хранилища по ключу. Если его нет ни там, ни там, задача остаётся непривязанной, и план говорит об этом.

### Повторный импорт

Задача находится по `key` в frontmatter, а не по имени файла.

| Состояние в хранилище | Что делает импорт |
|---|---|
| нет задачи с этим ключом | `create` |
| есть, `status: todo`, содержимое как в трекере | `current`, ничего не пишется |
| есть, `todo`, тикет изменился | `update`: переписываются только `Objective`, `Acceptance Criteria` и `Origin`, всё остальное в заметке — как было |
| есть, работа начата (`in-progress`, `blocked`, `review`, `done`, `cancelled`; у эпика — не `planned`) | `keep`: не трогается; если описание в трекере уже другое, план говорит и об этом |
| закрыто в трекере, в хранилище нет | `skip`, если не задан `--include-closed` |

## Почему так

**Снимок, а не синхронизация.** После импорта источник истины — задача в хранилище: она получает решения, свидетельства, `source`. Двусторонняя синхронизация сделала бы трекер писателем знания проекта, а это то, что [[Knowledge-OS/Protocols/Context-Provider-Protocol]] не разрешает внешней системе. Автоматический импорт по событию трекера — уже другое дело и требует Decision.

**Ключ, а не имя файла.** Имя задачи меняется (`sequence` пишет в него название), ключ трекера — нет. Поэтому повторный импорт не создаёт дубль, а `/mv-resume <ключ>` находит задачу при любой схеме имён.

**Текст тикета — данные.** Тикет пишет кто угодно. Скрипт ничего не исполняет, а команда прямо говорит ассистенту не действовать по тексту. В заметке он лежит под строкой о происхождении.

**Начатую работу не перезаписывать.** Задача, которую уже делают, накопила своё: результат, находки, решения. Изменение тикета после начала работы — расхождение, которое должен увидеть человек, а не правка, которую можно применить молча.

## Пример

```text
$ node "Knowledge-OS/Tools/mv.cjs" task-import --input import.json
Import from jira, 2 item(s); Tasks named by the next T-number.

  [create] E12-Billing-export.md  — PRJ-100: epic "Billing export"
  [create] T53-CSV-export-of-invoices.md  — PRJ-101: task "CSV export of invoices", in PRJ-100
  [link] E12-Billing-export.md  — PRJ-100: contains:: [[T53-CSV-export-of-invoices]]

This was a plan; nothing was written. Re-run with --apply to write it.
```

Так выглядит прогон на копии хранилища проекта-носителя 2026-10-26. После `--apply` валидатор не нашёл ошибок ни в задаче, ни в эпике. У эпика осталось предупреждение `orphaned-note`: на него ещё не ссылается список эпиков проекта.

## Подводные камни

- **Новый эпик — сирота**, пока список эпиков проекта на него не сошлётся. Команда предлагает эту строку; сам скрипт индексы проекта не правит.
- **Ключ из одних цифр** в YAML становится числом. Скрипт всегда пишет его в кавычках, но рукой поставленный `key: 1234` валидатор отклонит (`invalid-metadata-value`).
- **Шаблон проекта без `## Objective` или `## Acceptance Criteria`** — раздел добавляется в конец. Если шаблоны задач у копий разные (у апстрима короче, чем у проекта-носителя), импорт работает с любым.
- **Обновление сравнивает разделы, а не смысл.** Перенос строк в тикете — тоже изменение: задача в `todo` будет обновлена.

## Как менять

- **Новое поле из трекера** — сначала в нейтральную форму (команда, раздел «Normalise»), затем в `noteText()` и `refreshed()`, и тест в [[Knowledge-OS/Tools/task-import.test.mjs]].
- **Новая схема имён** — значение `tasks.keying` в `CONFIG_KEYS` валидатора, ветка в `plan()`, строка в таблице выше и в [[Docs/05-Project-OS/05-2-Delivery-Model]].
- **Двусторонняя синхронизация** — не правкой скрипта: это меняет, кто пишет знание проекта, и требует Decision.

# 6.10. Поиск задачи: task-lookup.mjs

> **Описывает:** [[Knowledge-OS/Tools/task-lookup.mjs]], [[Knowledge-OS/Tools/task-lookup.test.mjs]]; курсор рабочей копии; правила `duplicate-number` и `current-context-old-shape` в [[Knowledge-OS/Tools/validate-vault.mjs]]; `merge=union` для журнала метрик в `.gitattributes` хранилища
> **Связано:** [[Docs/05-Project-OS/05-2-Delivery-Model]] — что такое следующая задача, [[Docs/05-Project-OS/05-4-Session-Lifecycle]] — где поиск стоит в сессии, [[Docs/06-Tooling/06-9-Task-Import]] — блок `tasks` в `mvos.config.json`, [[Docs/06-Tooling/06-1-Validator]] — таблица правил

## Назначение

До os-v8 следующую задачу находил один `Grep` по frontmatter рабочей копии, а ответ ритуал закрытия записывал в `Current-Context.md`. Для одного человека этого хватало. Хранилище же живёт внутри проекта, а в проекте работают несколько человек. Тогда схема ломается дважды:

1. **Конфликт на каждом слиянии.** Каждая сессия переписывала `Current-Context.md` целиком. Две ветки двух людей меняли одни и те же строки, и при слиянии одна сторона теряла своё состояние.
2. **Одна задача на двоих.** Задача, взятая на чужой ветке, в рабочей копии остаётся `todo`, пока ветку не сольют. Поиск предлагал её следующему. В проекте-носителе так было с одним человеком: T35 дошла до `review` на своей ветке 2026-10-12, а поиск на `master` продолжал её предлагать.

Требования владельца (2026-10-26):
- решение не зависит от того, как команда работает с ветками: это меняется от проекта к проекту;
- накопленное знание общее для всех агентов и разработчиков;
- ничего не привязано к человеку.

Скрипт отвечает на четыре вопроса: на какой задаче эта рабочая копия, какие задачи свободны, какие взяты и где, какая следующая.

```bash
node "Knowledge-OS/Tools/mv.cjs" task-lookup                  # отчёт
node "Knowledge-OS/Tools/mv.cjs" task-lookup --json
node "Knowledge-OS/Tools/mv.cjs" task-lookup --take T36       # эта копия берёт задачу
node "Knowledge-OS/Tools/mv.cjs" task-lookup --take T36 --force
node "Knowledge-OS/Tools/mv.cjs" task-lookup --release        # копия ни на чём
```

`<задача>` для `--take` — имя файла (с `.md` или без), номер (`T36`) или `key`. Коды выхода: `0` — отчёт, задача взята или курсор снят; `1` — нет папки задач, имя не нашло задачу или нашло несколько, задача закрыта, задача взята в другом месте и `--force` не задан.

## Как работает

### Свободна, взята, закрыта

| Статус задачи | Значит |
|---|---|
| `done`, `cancelled` | закрыта |
| `todo` | свободна |
| любой другой (`in-progress`, `review`, `blocked`) | взята: работа начата |

Задача взята, если работа начата **здесь или на любой ветке, которую видит git и которая не слита в `HEAD`**: локальной или remote-tracking. Ветки перечисляет `git for-each-ref --no-merged HEAD refs/heads refs/remotes`, статусы на них читает один `git grep -z -e "^status:"` по папке задач, пачками по 50 веток. Слитая ветка уже содержится в `HEAD`, и её статус виден здесь.

**`done` или `cancelled` здесь закрывает задачу, что бы ни говорила ветка.** Ветка, слитая squash-ем, никогда не становится предком `HEAD`. Без этого правила её устаревший `in-progress` держал бы законченную задачу взятой навсегда.

Кто взял задачу, не записывается. Это и так говорит коммит, который поменял статус.

### Курсор рабочей копии

Какую задачу ведёт рабочая копия, — не знание, а положение курсора. Он лежит в собственном каталоге git, по пути `git rev-parse --git-path mvos/cursor.json`:
- в основной копии это `.git/mvos/cursor.json`, в worktree — `.git/worktrees/<имя>/mvos/cursor.json`, то есть у каждого worktree свой курсор;
- в git он не попадает никогда, и `.gitignore` для этого не нужен;
- без git курсор лежит в `.mvos/cursor.json` хранилища.

```json
{ "task": "T36-Graph-View", "taken": "2026-10-26" }
```

`--take` пишет только курсор. Поставить задаче `status: in-progress` и закоммитить — первый шаг самой работы ([[Project-OS/06-AI/AI]], «Taking a Task»). Другие увидят захват, когда этот коммит дойдёт до ветки, которую они получают через fetch. Достаточно отправить ветку, сливать её не нужно.

`--take` отказывает, если задача взята где-то ещё. `--force` нужен ровно в одном случае: это собственная незаконченная задача этой копии, а курсор потерян — новый клон или задача, взятая до os-v8.

### Следующая задача

1. Своя задача рабочей копии, пока она открыта.
2. Иначе при `tasks.next: lowest-number` — наименьшая по номеру свободная. Номер сравнивается как число: `T9` идёт раньше `T10`.
3. При `tasks.next: explicit` — никакая: задачу называет человек, а отчёт перечисляет свободные.

### Брошенный захват

Если файл взятой задачи не менялся `tasks.staleDays` дней (по умолчанию 14), отчёт помечает её «possibly abandoned». Дата — последний коммит, тронувший файл на той ветке, где задача взята. Незакоммиченная правка здесь считается сегодняшней. Что делать с такой задачей, решает владелец. Сам скрипт её не освобождает.

### Старая форма Current Context

Если в `Project-OS/06-AI/Context/Current-Context.md` есть раздел `## Current Task` или `## Current Goal`, отчёт говорит, что заметку надо перенести. Как переносить, описано в [[Project-OS/06-AI/AI]], «Current Context from before os-v8». То же сообщает валидатор предупреждением `current-context-old-shape`.

### Что ещё общее для всех

Одна задача на двоих — не единственное место, где сталкиваются две ветки. Оставшиеся два закрыты без нового инструмента:

- **Повторный номер.** Две ветки берут «следующий номер» и получают один и тот же: две `T53`. Git сливает два файла с разными именами молча. Правило валидатора `duplicate-number` проверяет уже слитое дерево — в pre-push или в CI, как бы ни работали с ветками. Оно сравнивает номера задач, эпиков, решений, ключи `key` и строки `U-NNN` реестра неопределённостей.
- **Журнал метрик.** Каждая закрытая сессия дописывает строку в конец `Metrics/Context-Metrics.md`, и две ветки пишут после одной и той же последней строки. `.gitattributes` хранилища задаёт этому файлу `merge=union`: git берёт строки обеих сторон. Тест «rows appended on two branches merge without a conflict» в `context-metrics.test.mjs` делает настоящее слияние; без этой строки то же слияние даёт конфликт.

## Почему так

**Курсор, а не файл на человека.** Файл `Context/<человек>.md` тоже снимает конфликты, но привязывает систему к человеку, а этого владелец не хотел. Идентификаторы клиентов ИИ (`userID` и `accountUuid` у Claude Code, `session_id` в хуках) не годятся: у каждого клиента свои, и есть они не у всех. Аккаунт — не человек. Постоянный идентификатор аккаунта в общем репозитории — персональные данные. Незаконченная работа живёт в рабочей копии: в ветке и незакоммиченных файлах. Продолжить её можно только там, поэтому единица — рабочая копия.

**Каталог git, а не `.mvos/`.** `.mvos/` в командной установке лежит в git проекта (`install.json`), и курсору там понадобилась бы строка игнорирования в каждом проекте. Путь от `--git-path` свой у каждого worktree и не отслеживается по построению.

**Все неслитые ветки, включая remote-tracking.** Это единственное, что одинаково при любом способе работать с ветками. Если команда работает на одном `master`, чужой захват приходит через `origin/master`, пока его не подтянули. Если у каждого своя ветка — через `origin/task/…`. Что git не видит (не отправлено, не получено), не видит никто. Скрипт сам не делает `git fetch`: сеть и права — не его дело.

**`union` для журнала, а не файл на сессию.** Строки журнала после записи не меняются, кроме повторного закрытия той же сессии. Поэтому объединение сторон — правильный ответ, и для него хватает одной строки `.gitattributes` вместо переписывания `context-metrics.mjs` и `/mv-trend`.

## Пример

Проект-носитель 2026-10-26, до переноса Current Context:

```text
$ node "Knowledge-OS/Tools/mv.cjs" task-lookup
Tasks: 52, 16 open. Next is chosen by tasks.next = lowest-number.

This working copy is on no Task.

Free (16): T36-Graph-View, T37-Node-Selection, …, T50-MVP-Demo, T52-Incremental-Map-Update

Next: T36-Graph-View — the lowest-numbered free Task.
  Take it when work starts: node "Knowledge-OS/Tools/mv.cjs" task-lookup --take T36-Graph-View

Current-Context.md still has `## Current Task` or `## Current Goal`: it predates the shared shape.
  Move it as Project-OS/06-AI/AI.md, "Current Context from before os-v8", says.
```

Если бы T37 взяли на ветке, отправленной в `origin`, в отчёте появился бы раздел:

```text
Taken, not by this working copy:
  T37-Node-Selection  in-progress  on origin/task/T37-node-selection, last changed 2026-10-26
```

## Подводные камни

- **Поиск статуса — строка, а не поле.** На ветках `git grep` ищет `^status:` и берёт первое совпадение в файле. Это строка frontmatter, потому что frontmatter идёт первым. Здесь же frontmatter разбирается YAML.
- **Курсор не переезжает с клоном.** Новый клон или удалённый `.git` — курсора нет. Отчёт тогда перечисляет задачи, взятые здесь, и подсказывает `--take <задача> --force`. Ассистент делает это только со слов человека ([[Knowledge-OS/Dist/commands/mv-resume]]).
- **Squash-слияние без удаления ветки.** Задача на `master` уже `done`, и правило «закрыто здесь» её не покажет. Но ветка остаётся в `--no-merged` и замедляет `git grep`. Слитые ветки лучше удалять.
- **`union` дублирует строку при одновременной правке.** Если одна ветка переписала последнюю строку журнала (повторное закрытие той же сессии), а другая дописала новую, слияние оставит обе версии переписанной строки. Следующий `--write` той же сессии заменит первую из них.
- **`Backlog.base` в Obsidian видит только рабочую копию.** Задача, взятая на чужой ветке, там остаётся `todo`.

## Как менять

- **Новый статус задачи.** Скрипт не перечисляет статусы, кроме закрывающих (`CLOSED`) и свободного (`FREE`). Новый статус автоматически означает «взята». Если это не так, правьте эти константы и `EPIC_TERMINAL_TASK_STATUS` в валидаторе вместе.
- **Другое правило следующей задачи.** Значение `tasks.next` в `CONFIG_KEYS` валидатора, ветка в `classify()`, строка таблицы в [[Docs/06-Tooling/06-9-Task-Import]] и тест.
- **Новая общая точка записи** — файл, который пишут все. Сначала решите, какой случай: журнал (`merge=union`), номер (`duplicate-number`) или состояние, которое надо разнести по сущностям, как Current Context.

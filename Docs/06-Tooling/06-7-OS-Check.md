# 6.7. os-check: определение готовности одной командой

> **Описывает:** [[Knowledge-OS/Tools/os-check.mjs]], [[Knowledge-OS/Tools/os-check.test.mjs]], [[Knowledge-OS/Tools/run-tests.mjs]], `.github/workflows/os-check.yml`, скрипты `os:check` и `test` в [[package.json]]
> **Связано:** [[Docs/10-Extending]] — определение готовности («Готово, когда»), которое эта команда проверяет, [[Docs/06-Tooling/06-1-Validator]] — первый шаг и правила `broken-md-link`, `docs-link-outside-os-layer`, `undocumented-os-file`, [[Docs/06-Tooling/06-6-Tests-and-Fixtures]] — второй шаг, [[Docs/08-Distribution/08-2-Adoption]] — четвёртый шаг (`adopt.mjs --verify`), [[Docs/06-Tooling/06-2-Stale-Check-and-Graph-Report]] — пятый шаг, [[Docs/08-Distribution/08-4-Versioning-and-Changelog]] — что считается записью в CHANGELOG

## Назначение

Изменение слоя ОС готово, когда выполнены три условия: документация актуальна, связи целы, скрипты работают ([[Docs/10-Extending]], «Готово, когда»). До `os-check.mjs` это были три привычки, и проверял их тот, кто помнил. Привычки сбоили: `Docs/08-4` называл `os-v4` версией после выхода os-v5, а новый тестовый файл не попадал в `npm test`, пока его не вписывали вручную. `os-check` собирает в одном месте всё, что из определения готовности способна проверить машина.

```bash
npm run os:check                                           # из корня хранилища
node "Knowledge-OS/Tools/os-check.mjs" --range origin/master..HEAD
node "Knowledge-OS/Tools/os-check.mjs" --skip tests,syntax  # пропустить шаги
npm run check                                               # в проекте-носителе: os-check + сборка, тесты и линтер проекта
```

Код выхода: `0` — каждый шаг прошёл или пропущен; `1` — хотя бы один шаг не прошёл.

## Как работает

Шесть шагов, по порядку. Каждый выполняется, даже если предыдущий упал, поэтому один прогон называет все проблемы сразу.

| # | Шаг | Что проверяет | Когда пропускается |
|---|---|---|---|
| 1 | `validate-vault` | `validate-vault.mjs` без ошибок: схема, wikilink- и Markdown-ссылки, ссылки `Docs/` только на слой ОС, каждый инструмент и команда упомянуты в `Docs/`, манифест | никогда |
| 2 | `tests` | `run-tests.mjs`: каждый `*.test.mjs` под `Knowledge-OS/` | `--skip tests` |
| 3 | `syntax` | каждый `.mjs`/`.cjs` слоя проходит `node --check` (фикстуры и `node_modules` не в счёт) | `--skip syntax` |
| 4 | `deployment` | `adopt.mjs --verify --only commands,hooks`: развёрнутые копии совпадают с `Dist/` | когда ОС никуда не развёрнута — все расхождения имеют вид `create` (апстрим, свежий клон) |
| 5 | `graph` | `graph-report.mjs --json`: число заметок, компонент связности, изолированных; **только сообщает**, никогда не валит | `--skip graph` |
| 6 | `docs-with-code` | по каждому коммиту диапазона: коммит, меняющий `Knowledge-OS/Tools/`, `Dist/`, `Schema/`, `Rules/` или `Protocols/` (тесты и фикстуры не в счёт), обязан менять `Docs/` или нести трейлер `Docs: none — <причина>`; диапазон с такими коммитами обязан менять `CHANGELOG.md` | нет git; у `HEAD` нет upstream и не передан `--range` |

### Шаг 6 подробнее

Диапазон по умолчанию — `@{u}..HEAD`: то, что ещё не отправлено. Ровно это проверяет pre-push хук проекта-носителя. В CI диапазон передаётся явно: для pull request — от базы, для push — от `github.event.before`.

Коммиты берутся командой `git rev-list --no-merges <range> -- .`, запущенной из каталога хранилища. Поэтому в встроенной раскладке коммиты проекта, не трогавшие хранилище, в счёт не идут. Пути каждого коммита читает `git diff-tree --relative`: они относительны хранилища в обеих раскладках.

Сама логика — чистая функция `checkDocsWithCode(commits)`, она экспортируется. Пути классифицируют предикаты `isCodePath` и `isDocsPath`.

Трейлер обязан содержать причину. Голое `Docs: none` — та же привычка, ради отмены которой написана проверка, только записанная трейлером.

### Подключение

- **Проект-носитель.** Корневой `npm run check` начинается с `npm run os-check` (то есть `os:check` в workspace хранилища). `check` запускает pre-push хук `.githooks/pre-push`.
- **Апстрим.** `.github/workflows/os-check.yml` гоняет `os-check` на Ubuntu и Windows с Node 18 и 22, с `fetch-depth: 0`: шагу 6 нужна история. Файл назван в манифесте и уезжает в каждую копию. В установленном проекте он ничего не делает: хранилище там подпапка, а GitHub читает workflow только из `.github/` корня репозитория.

### `run-tests.mjs`

Ищет каждый `*.test.mjs` под `Knowledge-OS/`, кроме `__fixtures__/`, `__provider_fixtures__/`, `node_modules/` и dot-каталогов. Найденное передаёт одному вызову `node --test` через `process.execPath`. `--list` печатает список и ничего не запускает; слово-фильтр сужает список до файлов, в пути которых оно встречается. Подробнее — [[Docs/06-Tooling/06-6-Tests-and-Fixtures]].

## Почему так

**Одна команда, а не шесть.** Определение готовности, которое надо собирать из шести команд, на шестой забывают. Сводная команда, которую ещё и запускает хук, проверяется при каждой отправке.

**Все шаги, даже после падения.** Первая ошибка обычно не единственная. Прогон, который останавливается на ней, превращает исправление в цикл «починил — запустил — нашёл следующее».

**Граф только сообщает.** Число компонент — описание, а не дефект: на свежем хранилище законно бывает остров. Гейт из описания, который обычно красный, перестают читать (сквозной принцип [[Docs/06-Tooling/06-1-Validator]]).

**Проверка по коммитам, а не от тега.** Сравнение «с последнего `os-vN`» накопительно: одна правка CHANGELOG закрыла бы все последующие изменения. Кроме того, тег `os-v5` в проекте-носителе и в апстриме указывает на разные коммиты, а мелкий клон CI тегов не видит вовсе.

**Наполовину.** Шаг 6 видит, что `Docs/` тронуты, но не видит, что тронуты правильно. Это сознательная граница. Машина делает дешёвую часть, а смысл остаётся за тем, кто вносит изменение.

## Пример

```text
os-check — /work/project/MemoValeOS  (os-v5)

  [1/6] ok   validate-vault  OK — no schema violations.
  [2/6] ok   tests           tests 212, pass 212, fail 0
  [3/6] ok   syntax          29 file(s) parse
  [4/6] ok   deployment      deployed copies in /work/project match Dist
  [5/6] info graph           175 notes, 1 connected component(s), 0 isolated
  [6/6] FAIL docs-with-code  range @{u}..HEAD
           1a2b3c4 "Speed up the walk" changes Knowledge-OS/Tools/validate-vault.mjs but not Docs/, and carries no "Docs: none — <reason>" trailer

1 step(s) failed — the change is not done (Docs/10-Extending.md, "Готово, когда").
```

Есть два выхода. Первый — описать изменение на странице `Docs/`, которая описывает этот инструмент. Второй — если изменение действительно ничего не меняет для читателя, дописать в сообщение коммита трейлер `Docs: none — внутренняя перестановка, поведение то же`.

## Подводные камни

- **Нет upstream — нет шага 6.** На ветке без отслеживаемой ветки диапазона нет, и шаг пропускается с подсказкой. Чтобы проверить такую ветку, передайте `--range`.
- **Слияния не проверяются** (`--no-merges`). Коммиты ветки задачи попадают в диапазон сами по себе, а коммит слияния ничего своего не вносит.
- **`deployment` смотрит только `commands` и `hooks`.** Редирект в `CLAUDE.md`, настройки и `.gitignore` проверяет полный `adopt.mjs --verify`.
- **Время.** Шаги 1 и 2 занимают основную часть прогона: тесты строят временные git-репозитории.

## Как менять

- **Новый шаг** — функция `step…()`, возвращающая `{status: "ok" | "fail" | "skip" | "info", detail, lines?}`, плюс строка в массиве `steps` внутри `main()`, строка в таблице выше и тест в `os-check.test.mjs`, если у шага есть собственная логика.
- **Что считается кодом для шага 6** — `CODE_PREFIXES` и `isCodePath`. Меняйте их вместе с тестом «which paths count as code».
- **Матрица CI** — `.github/workflows/os-check.yml`. Нижний Node матрицы — это пол, который обещает README.

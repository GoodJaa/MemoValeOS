# 08-2. Развёртывание в проект: `adopt.mjs` и `Dist/`

> **Описывает:** [[Knowledge-OS/Tools/adopt.mjs]], [[Knowledge-OS/Tools/adopt.test.mjs]], [[Knowledge-OS/Tools/build-plugin.mjs]], [[Knowledge-OS/Tools/build-plugin.test.mjs]], плагин `Knowledge-OS/Dist/plugin/` и маркетплейс `.claude-plugin/marketplace.json`, содержимое `Knowledge-OS/Dist/` ([[Knowledge-OS/Dist/CLAUDE.redirect.md]], [[Knowledge-OS/Dist/settings.fragment.json]], [[Knowledge-OS/Dist/hooks/budget-audit.cjs]], `Knowledge-OS/Dist/commands/mv-*.md`), протокол [[Knowledge-OS/Protocols/Deployment-Protocol]] и команду [[Knowledge-OS/Dist/commands/mv-adopt.md]].
> **Связано:** [[Docs/02-System-Layout]] — два корня и две раскладки, [[Docs/08-Distribution/08-1-OS-Manifest]] — почему `.claude/` не в манифесте, [[Docs/07-Commands]] — что разворачивается, [[Docs/06-Tooling/06-4-Budget-Audit-Hook]] — что делает хук, [[Docs/06-Tooling/06-1-Validator]] — правила расхождения копий.

## Назначение

Claude Code загружает slash-команды, хуки и настройки из `.claude/` в **корне проекта**. А слой ОС доставляется патчем путей манифеста, а они относительны хранилища: доставка несёт только **содержимое хранилища**. Одно место не может служить и транспорту, и загрузчику. Поэтому копий две:

- **исходник** в `Knowledge-OS/Dist/` — внутри хранилища, едет вместе со слоем ОС;
- **развёрнутая копия** в `<project>/.claude/` — то, что реально читает Claude Code.

`adopt.mjs` превращает первое во второе. Правило валидатора `deployed-command-drift` следит, чтобы копии не разошлись.

До os-v3 этого механизма не было. Манифест объявлял `.claude/**` слоем ОС, транспорт его не нёс, и тот, кто клонировал апстрим, получал систему без единой команды. Ничто об этом не сообщало.

Копирование годится для команды, которая принимает ОС целиком. Для одного человека в чужом проекте оно не годится: оно правит общий `CLAUDE.md`, `settings.json` и `.gitignore`. Первая реальная установка (2026-10-13) собирала личный вариант вручную. С 2026-10-26 у `adopt.mjs` два режима, и личный ставит плагин вместо копий.

## Как работает

### Два режима

| | `--team` | `--local` |
|---|---|---|
| Для кого | команда принимает ОС вместе | один человек в проекте, которым владеет команда |
| Команды и хук | копии в `.claude/commands/`, `.claude/hooks/`; запись хука в `.claude/settings.json` | плагин Claude Code `mv` из маркетплейса-хранилища ([ниже](#плагин-mv-команды-без-копий)); ставит владелец командами `claude plugin …` |
| Имена команд | `/mv-check`, `/mv-close`… | `/mv:check`, `/mv:close`… |
| Точка входа ассистента | редирект в маркерах сверху `CLAUDE.md` | свой файл `.claude/rules/memovaleos.md`; `CLAUDE.md` проекта не трогается и грузится как раньше |
| Исключения из git | две строки в `.gitignore` (общий файл) | блок в маркерах в `.git/info/exclude` (только этот клон): хранилище, файл rules, артефакты бюджета, `settings.local.json` |
| Классы | `commands`, `hooks`, `settings`, `claude-md`, `gitignore` | `plugin`, `rules`, `exclude`; по флагу `--exclude-host-claude-md` ещё `host-claude-md` |
| Проверка | `--verify`: развёрнутое совпадает с `Dist/` | `--verify`: rules, exclude и плагин на месте; `git status` пуст |

Почему файл `rules`, а не `CLAUDE.local.md`: если в проекте есть `CLAUDE.local.md`, Claude Code перестаёт читать `AGENTS.md`, а у человека этот файл уже может быть свой. `.claude/rules/*.md` грузятся так же и ничего не скрывают, а удалить такой файл можно целиком.

#### `CLAUDE.md` команды — только из хранилища: `--exclude-host-claude-md`

При личной установке `CLAUDE.md` команды грузится рядом с файлом rules. Это верно, пока его правила живут только там. Когда владелец разложил их в унаследованные решения (`origin: inherited`, [[Knowledge-OS/Protocols/Deployment-Protocol]] §7), грузить обе копии значит дважды тратить контекст на одни и те же правила: на первом реальном проекте файл занимал 404 строки. Флаг убирает файл из сессий этого человека, а команде и самому файлу ничего не меняет:

```bash
node "<хранилище>/Knowledge-OS/Tools/mv.cjs" adopt --apply --local --exclude-host-claude-md
```

- **Что пишется.** Одна строка в `claudeMdExcludes` файла `.claude/settings.local.json`: абсолютный путь к `CLAUDE.md` проекта с прямыми слэшами и в настоящем регистре (`realpathSync.native`). На Windows буква диска пишется в обе стороны: `{G,g}:/…/CLAUDE.md`. Остальные ключи файла, в том числе allow-правила Claude Code, сохраняются.
- **Сначала решения, потом исключение.** Если в `Project-OS/` нет ни одного Decision с `origin: inherited` и `source`, который называет этот `CLAUDE.md` по пути в репозитории, класс отказывает: иначе правила команды пропали бы из контекста, а на их месте ничего бы не было. Взять на себя этот риск можно флагом `--yes`.
- **Только для личной установки.** В командной редирект на хранилище сам лежит в `CLAUDE.md`, поэтому с `--team` флаг даёт код 1.
- **Класс остаётся в силе.** Однажды применённый класс записан в `install.json`, поэтому повторный `--apply` его сохраняет, а `--uninstall` снимает без флага. Снимается только наша строка, и файл, в котором ничего не осталось, удаляется.
- **Это не запрет на чтение.** `claudeMdExcludes` убирает файл из того, что Claude Code грузит при запуске. Прочитать его по просьбе ассистент может по-прежнему.

Поведение Claude Code проверено запуском (2.1.310, Windows, 2026-10-26, `claude -p` с выключенными инструментами на временном хосте с кодовым словом в `CLAUDE.md`). Без исключения ответ — кодовое слово. Шаблоны `C:/…/CLAUDE.md`, `C:\…\CLAUDE.md`, `**/…/CLAUDE.md` и `{C,c}:/…/CLAUDE.md` убирают файл. `c:/…` не убирает, потому что совпадение чувствительно к регистру. После `adopt --uninstall --apply` кодовое слово вернулось. Если оставить ассистенту инструменты, он сам читает `CLAUDE.md`, и проверка ничего не показывает.

**Какой режим.** Режим задаёт флаг. Без флага берётся режим из записи установки, а если в проекте уже стоит командная установка — `team`. Проект не под git может быть только `team`: личной установке нечем прятаться от git. Если ничто из этого не сработало, план строится для рекомендованного режима и объясняет выбор (строка `Mode`). В git-проекте рекомендуется `local`, особенно когда `CLAUDE.md` отслеживается. `--apply` без режима отказывает с кодом 1. Режим `local` в самостоятельной раскладке тоже отказ: у хранилища, которое само проект, нет хоста, которого нельзя трогать.

**Применяет владелец.** План кончается готовой командой применения, например `node "<хранилище>/Knowledge-OS/Tools/mv.cjs" adopt --apply --local`, и, для личной установки, командами Claude Code:

```bash
cd "<корень проекта>"
claude plugin marketplace add "<хранилище>" --scope local
claude plugin install mv@memovaleos --scope local
```

`/mv-adopt` только строит план и передаёт эти команды человеку. `--apply` пишет в `.claude/` и `.git/`, а это защищённые пути для ассистента. На первой реальной установке классификатор отклонял такие записи, и владелец делал их сам, не зная заранее, какие именно. Команды `claude plugin …` меняют конфигурацию самого Claude Code. Классы `plugin` в плане имеют действие `owner`: `--apply` их не выполняет, а печатает снова в конце.

### Удаление: `--uninstall`

`--uninstall` строит план снятия, `--uninstall --apply` его выполняет. Режим берётся так же, как для установки. Снимается только то, что доказуемо наше (`provablyOurs()`): файл, чей sha256 записан в `install.json`, или файл, совпадающий с исходником в `Dist/`. Файл, отредактированный после установки, без `--yes` даёт отказ с кодом 2.

Порядок такой, чтобы хост нельзя было оставить сломанным:
1. в личной установке — сначала шаги владельца: `claude plugin uninstall mv@memovaleos --scope local` и `claude plugin marketplace remove memovaleos`;
2. запись хука из `settings.json` — раньше файла хука. Хук, названный в настройках без файла за ним, падает на каждом чтении. Если в файле настроек не остаётся ничего, файл удаляется;
3. команды, хук и файл rules;
4. наши блоки из файлов проекта: редирект вместе с пустой строкой под ним, строки `.gitignore`, блок `.git/info/exclude`, строка `claudeMdExcludes` в `settings.local.json`. Окружающий текст возвращается байт в байт, а файл, в котором ничего не осталось, удаляется;
5. запись установки — последней.

Хранилище не удаляется никогда, как и копия `CLAUDE.md` хоста в его Inbox. Тесты: «--uninstall after --team gives the host back byte for byte», «--uninstall after --local takes out exactly what went in», «--uninstall leaves a command edited since install, and says so».

### Что лежит в `Dist/`

| Файл | Куда разворачивается | Класс |
|---|---|---|
| `commands/mv-*.md` (11 штук) | `<project>/.claude/commands/` | `commands` |
| `hooks/budget-audit.cjs` (без `*.test.mjs`) | `<project>/.claude/hooks/` | `hooks` |
| `settings.fragment.json` | сливается в `<project>/.claude/settings.json` | `settings` |
| `CLAUDE.redirect.md` | блок в начале `<project>/CLAUDE.md` | `claude-md` |
| — (строки в коде) | две строки в `<project>/.gitignore` | `gitignore` |

`hooks/budget-audit.test.mjs` остаётся в `Dist/`: тест едет в апстрим вместе с хуком, но проекту-хосту он не нужен.

### Принцип: скрипт пишет в дерево, которое ему не принадлежит

Из этого факта следует каждое ограничение (шапка `adopt.mjs` и §4–5 протокола):

- режим по умолчанию — **план**, без `--apply` не пишется ни байта, а применяет план человек;
- пишутся только имена `mv-*`, хук, `.claude/rules/memovaleos.md` и текст между нашими маркерами. Всё остальное в `.claude/` принадлежит проекту;
- `.claude/agents/` не трогается вообще. `.claude/settings.local.json` пишет сам Claude Code, и плагин в нём регистрирует его же команда; `adopt` добавляет туда одну строку `claudeMdExcludes`, и только по флагу `--exclude-host-claude-md`;
- нечитаемый `settings.json` остаётся байт в байт прежним: «переписать файл, который не удалось прочитать, — то, как установщик уничтожает чужую работу»;
- удаление — только по `--uninstall` и только доказуемо нашего; ничего не индексируется и не коммитится;
- `mv-*`-копия, отличающаяся от исходника, не перезаписывается без `--yes`: это наша устаревшая копия, но её могли править намеренно;
- файл проекта, куда дописывается блок, сохраняет свои окончания строк. В checkout с `autocrlf` на диске CRLF; текст обрабатывается с LF и на выходе приводится к окончаниям файла (`eolOf`, `asEol`). Иначе установка переписала бы каждую строку файла, в который добавила один блок, а удаление не вернуло бы его байт в байт.

### Корни

`detectProjectRoot()` перебирает источники по порядку и пишет, какой сработал (строка переписи `project root from`):
1. `--project <dir>`;
2. `--standalone` — хранилище само проект;
3. запись установки `<хранилище>/.mvos/install.json`;
4. `git rev-parse --show-toplevel` от хранилища;
5. родитель хранилища. Так скрипт работает и вне git, например на фикстурах.

Если хранилище оказалось **вне** найденного корня проекта, скрипт отказывается с кодом 1: значит, определение ошиблось, а развёртывание в чужое рабочее дерево — ровно та ошибка, ради которой скрипт существует. В самостоятельной раскладке корни совпадают, и это законно: так дистрибутивный репозиторий получает собственные команды.

**Вложенный `.git` — отказ, а не догадка.** Если хранилище — корень собственного git-репозитория, а его родитель лежит внутри другого, скрипт без `--project` или `--standalone` выходит с кодом 1 и печатает обе команды. Именно так выглядела первая реальная установка: клон дистрибутива со своим `.git` в репозитории проекта. Правило toplevel взяло хранилище за проект и развернуло `.claude/` внутрь него, туда, где Claude Code ничего не читает. Оба прочтения законны, поэтому выбирает человек. Тест: «a vault with its own .git inside another repository is refused until a root is named».

**Хранилище ниже корня репозитория — тоже отказ.** Хранилище может лежать не в корне, а глубже, например в пакете монорепо: `packages/api/MemoValeOS`. Тогда без `--project` скрипт выходит с кодом 1 и предлагает два корня: корень репозитория и папку, где лежит хранилище. Правило toplevel поставило бы всё в корень репозитория, но это верно, только если Claude запускают оттуда (таблица ниже). Откуда его запускают, скрипт не видит, поэтому выбирает человек. Выбор попадает в запись установки, и следующие запуски берут корень из неё. Тест: «a vault below the top of its repository is refused until the start folder is named».

#### Корень проекта — папка, где запускают Claude

Claude Code читает свои файлы из разных мест. Таблица составлена по его документации (страницы memory, settings, large-codebases, worktrees, проверено 2026-10-26):

| Файл | Claude запущен в пакете монорепо | Claude запущен в linked worktree |
|---|---|---|
| `CLAUDE.md` | папка запуска и все папки выше | из worktree |
| `.claude/rules/*.md` | папка запуска; о папках выше документация прямо не говорит | из worktree |
| `.claude/settings.json` — хук командной установки | только папка запуска, от папок выше не наследуется | из worktree |
| `.claude/settings.local.json` — плагин личной установки | корень репозитория; на Windows и в версиях до 2.1.211 — папка запуска | корень основного checkout; на Windows — worktree |
| `.claude/commands/` | как skills: папка запуска и папки выше до корня репозитория | worktree, а если там нет `.claude/commands` — основной checkout |

Отсюда правило: **корень проекта — та папка, где запускают Claude**. Командная установка с `--project packages/api` пишет `.claude/`, `CLAUDE.md` и `.gitignore` пакета, а корень репозитория не трогает. Хук тогда лежит там, где сессия из пакета читает настройки.

Личная установка в пакете учитывает ещё два места:
- **Строки `exclude` отсчитываются от корня репозитория.** Шаблон с ведущим `/` в `.git/info/exclude` якорится у корня репозитория, а не у корня проекта. Поэтому скрипт добавляет к строкам путь проекта внутри репозитория (`git rev-parse --show-prefix`), например `/packages/api/MemoValeOS/`. До 2026-10-26 строки шли от корня проекта, и установка в пакет оставляла хранилище в `git status`. Нашёл это тест монорепо. В обычном случае путь проекта пуст, и блок не меняется.
- **Плагин ищется в обоих местах `settings.local.json`.** План, перепись и `--verify` смотрят файл в папке запуска и в корне основного checkout (первая строка `git worktree list`). Шаги владельца печатаются после `cd "<корень проекта>"`: `claude plugin install --scope local`, запущенный оттуда, кладёт запись туда, где Claude Code будет её искать для этой папки.

### Запись установки: `.mvos/install.json`

Каждое применение (`--apply`) последним шагом пишет в хранилище запись о том, что установлено. Пишет по тому, что лежит на диске, а не по плану:

```json
{
  "format": 1,
  "osVersion": "os-v5",
  "mode": "team",
  "projectRoot": "..",
  "installedAt": "2026-10-26",
  "files": [{ "path": ".claude/commands/mv-check.md", "class": "commands", "sha256": "…" }],
  "blocks": [{ "path": "CLAUDE.md", "class": "claude-md", "marker": "<!-- MemoValeOS:redirect:begin -->" }]
}
```

- **`projectRoot`** — путь к корню проекта от хранилища. Его читают следующие запуски `adopt.mjs`, а также `validate-vault.mjs` (`findClaudeDir`, `findRepoRoot`, признак дистрибутивной копии) и `stale-check.mjs`. С записью хранилище со своим `.git` спрашивает о `source` репозиторий проекта, а не свой.
- **`mode`** — `team` (копирование), `standalone` (хранилище само проект). В режиме `local` (плагин) валидатор не сравнивает `Dist/` с `.claude/`: копий там нет.
- **`files`** — каждый развёрнутый `mv-*` и хук с sha256 по содержимому с LF, чтобы `autocrlf` не выглядел как локальная правка. **`blocks`** — наши вставки в файлы проекта: редирект, запись хука в `settings.json`, блок `.gitignore`. По ним удаление будет знать, что снимать и что трогать нельзя.
- `installedAt` сохраняется от первой записи. Запись переписывается, только если изменилось содержимое, поэтому повторный `--apply` ничего не трогает.
- План показывает её строкой `[record] create|update|overwrite` или в «Unchanged». `update` — когда изменились корень проекта, режим или версия ОС: после `upgrade.mjs` запись ещё называет прежнюю, пока установку не применят заново. `--verify` её не проверяет: она описывает установку, а не исходники.
- Запись — состояние одной установки. Она не в манифесте и не в `PER_COPY_FILES` и никуда не едет. В командной установке она лежит в git проекта вместе с хранилищем.
- Рядом с ней `upgrade.mjs` пишет `.mvos/os-base.json` — хеши версии, взятой последним обновлением; это база следующего ([[Docs/08-Distribution/08-3-Upstream-Sync-and-Upgrade]]). Режим из записи решает, какие шаги владельца обновление напечатает: заново применить установку или обновить плагин.

### История хранилища при личной установке

При `--local` хранилище исключено из git проекта (`info/exclude`), и у знания нет другой истории. Поэтому рекомендован **свой `.git` у хранилища, без remote апстрима** (решение владельца 2026-10-25): это история заметок проекта, а не способ получать обновления. Обновление идёт сравнением файлов (`mv.cjs upgrade --from github:GoodJaa/MemoValeOS@os-vN`), и общая с апстримом история ему не нужна. Remote апстрима в такой копии вредит: `git pull` смешал бы публичную историю ОС с приватным знанием проекта. Корень проекта при вложенном `.git` берётся из записи установки (выше), поэтому свой `.git` хранилища больше не сбивает ни `adopt.mjs`, ни валидатор.

### Классы по отдельности

**`commands` и `hooks`** — одна операция `planCopies()` с разными фильтрами имён (`isMv()` и `*.mjs` без `*.test.mjs`). Для каждого файла сравнивается содержимое после нормализации CRLF → LF:

| Состояние цели | Действие |
|---|---|
| файла нет | `create` |
| совпадает с исходником | без изменений (`already identical`) |
| отличается, есть `--yes` | `overwrite` |
| отличается, нет `--yes` | отказ: `differs from Dist; pass --yes to overwrite` |

**`settings`.** Блок хука берётся из `settings.fragment.json` (`fragmentHook()`), а не пишется в коде, поэтому форма развёрнутого и исходного не может разойтись.
- нет `settings.json` — создаётся `{ hooks: { PreToolUse: [<фрагмент>] } }`;
- JSON не разбирается — **отказ**, файл не тронут, остальные классы продолжаются;
- среди хуков `PreToolUse` ровно одна наша запись (`ourHookEntries()`: любая, чей JSON содержит `budget-audit.`), и она совпадает с фрагментом (`sameHook()`: `type`, `command`, `args`, `timeout`) — ничего не делается. Это и есть идемпотентность: повторное применение не дублирует хук;
- наша запись есть, но старой формы — например, shell-форма `node "$CLAUDE_PROJECT_DIR/.claude/hooks/budget-audit.mjs"` во всех проектах, установленных до 2026-10-25, — действие **`replace`**: первая наша запись заменяется текущей на том же месте среди хуков хоста, остальные наши удаляются, matcher без хуков исчезает. `--verify` считает `replace` расхождением;
- иначе хук добавляется в существующий matcher `Read|Grep|Glob` или новым matcher'ом в `PreToolUse`.

Фрагмент — в **exec-форме**: `"command": "node"`, `"args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/budget-audit.cjs"]`. Claude Code запускает её без оболочки и подставляет `${CLAUDE_PROJECT_DIR}` сам. В shell-форме переменную раскрывала оболочка, а на Windows без Git Bash это PowerShell, где `$CLAUDE_PROJECT_DIR` — пустая переменная PowerShell. Там же упавший хук `PreToolUse` может *блокировать* вызов инструмента: без Git Bash вердиктом считаются только коды 0 и 2.

**`hooks`, переименование.** Хук назывался `budget-audit.mjs` до 2026-10-25. Развёрнутую копию со старым именем установщик не удаляет: удалять он не умеет вообще. Он называет её в разделе «Unchanged»: `an older version of the hook; once settings no longer name it, delete it by hand` (`OLD_HOOK_NAMES`). Валидатор сообщает о ней `undeployed-command-source`.

**`claude-md`.** В самостоятельной раскладке (корень проекта = хранилище) класс ничего не делает: `CLAUDE.md` хранилища — сама точка входа, и редирект на себя переложил бы её в `Inbox/` как чужую. План пишет об этом строкой `standalone layout: the vault's own CLAUDE.md is the entry point; no redirect`. Во встроенной раскладке текст редиректа берётся из [[Knowledge-OS/Dist/CLAUDE.redirect.md]]. Записанное там `MemoValeOS/` (имя папки в проекте, где систему писали) заменяется настоящим путём хранилища относительно корня проекта, поэтому хранилище под другим именем получает рабочий редирект. Блок оборачивается маркерами:

```markdown
<!-- MemoValeOS:redirect:begin -->
This project's knowledge system lives in `MemoValeOS/`.

Read `MemoValeOS/CLAUDE.md` first — it is the real entry point and defines how to use Knowledge OS and Project OS. Follow it, not this file.
<!-- MemoValeOS:redirect:end -->
```

| Состояние `<project>/CLAUDE.md` | Действие |
|---|---|
| нет | `create`: только блок |
| уже содержит маркер `begin` | ничего |
| текст равен редиректу, но без маркеров | `mark`: маркеры вокруг того же текста. Так выглядит любой проект, где систему ставили руками, включая тот, где её писали; переносить такой текст в Inbox значило бы подшить редирект как чужое знание |
| пуст | `prepend`: блок |
| свой текст хоста | `prepend` блока **и** перенос прежнего тела дословно в `Project-OS/Inbox/Adopted CLAUDE.md` со строкой происхождения (откуда, кем, когда) |

Скрипт сознательно останавливается на переносе. Решить, что из чужих инструкций — Decision, что — Architecture, а что — соглашение проекта, — это суждение. Это делает `/mv-adopt` с человеком, по одному пункту ([[Knowledge-OS/Protocols/Deployment-Protocol]], §6). Пока пункт не разобран, он остаётся в Inbox: «неразложенная заметка честна, а разложенная не туда — ложное утверждение о том, что проект решил». Валидатор не требует frontmatter в `Inbox/` и не проверяет там ссылки.

**`gitignore`.** Дописываются строки `.claude/budget-audit.jsonl` и `.claude/budget.json` с комментарием: это артефакты одной сессии, а не исходники.

### Перепись

Перед планом печатается перепись: что на проекте уже есть. Это `CLAUDE.md`, `.claude/commands/` (сколько файлов наши, сколько проекта), `hooks/`, `agents/`, состояние `settings.json` и версия слоя из `.os-version`. До появления этой строки у `.os-version` не было ни одного читателя. Он говорил `os-v1`, когда CHANGELOG дошёл до os-v2, и никто не заметил.

Дальше идут факты предполётной проверки:
- откуда взят корень и есть ли запись установки;
- свой ли `.git` у хранилища и отслеживается ли `CLAUDE.md`;
- есть ли `CLAUDE.local.md`, `AGENTS.md`, `settings.local.json`, `.claude/skills/` и `.claude/rules/`;
- в личной установке — включён ли плагин и грузится ли `CLAUDE.md` команды;
- **`other knowledge`** — признаки чужой системы знаний (`otherKnowledgeSigns()`).

Последняя строка складывается так:
- маркеры других инструментов: `memory-bank/`, `.cursor/rules`, `.cursorrules`, `.windsurf/rules`, `.windsurfrules`, `.clinerules`, `.kiro`, `.github/copilot-instructions.md`;
- `docs/`, если в нём от 50 markdown-файлов (`LARGE_DOCS`);
- число хуков в `settings.json`, которые не наши.

Ничего из этого установка не трогает. Строка отсылает к [[Knowledge-OS/Protocols/Deployment-Protocol]] §10: систему не удалять, назвать её ресурсом и ссылаться на неё. На первом реальном проекте владелец нашёл чужой хук, скиллы и около 3500 файлов задач в `docs/` сам, по ходу установки. Тест: «the census names another knowledge system and leaves it alone».

### Режимы и коды выхода

| Вызов | Что делает | Код выхода |
|---|---|---|
| без флагов | перепись + план, ничего не пишет; в конце — команда применения | 0 |
| `--local` / `--team` | выбирает режим ([«Два режима»](#два-режима)) | 1, если указаны оба |
| `--apply` | применяет все классы режима | 0 — сделано; 1 — режим не выбран; 2 — применено, но шаг отказал |
| `--uninstall` | план снятия; с `--apply` — снятие | 0; 2 — что-то наше отредактировано и оставлено |
| `--exclude-host-claude-md` | личная установка: класс `host-claude-md`, `CLAUDE.md` проекта перестаёт грузиться в сессиях этого человека (раздел «`CLAUDE.md` команды — только из хранилища» выше) | 1 с `--team`; 2, если в хранилище нет унаследованного решения из этого файла, а `--yes` не задан |
| `--language <тег>`, `--notes <политика>` | создаёт или обновляет `mvos.config.json` в хранилище: язык проекта для [[Knowledge-OS/Rules/Communication-Rules]] и язык заметок (`language`, `english`, `split`); остальные ключи файла сохраняются. Без флагов план только называет текущий язык | 1, если тег или политика не того вида |
| `--apply --only commands,hooks` | только перечисленные классы | то же. Неизвестный класс — 1 |
| `--verify` | `team`: сравнивает развёрнутое с `Dist/`, расхождение — любой `create`, `overwrite`, `replace` или отказ; `local`: расхождение — всё, чего установке не хватает, включая неустановленный плагин | 0 — совпадает; 1 — расхождение |
| `--yes` | разрешает перезапись устаревших `mv-*` | — |
| `--project <dir>` | явный корень проекта | 1, если хранилище вне него |
| `--standalone` | хранилище само проект: развёртывание внутрь него | — |
| (без `--project`/`--standalone`, у хранилища свой `.git` внутри другого репозитория, записи нет) | отказ с обеими командами | 1 |
| (без `--project`, хранилище ниже корня своего репозитория, записи нет) | отказ с двумя корнями: репозиторий и папка хранилища | 1 |
| `--json` | машиночитаемый вывод | — |

### Правила валидатора, которые держат копии вместе

| Правило | Уровень | Когда |
|---|---|---|
| `deployed-command-drift` | ошибка | `Dist/commands/mv-*.md` или `Dist/hooks/budget-audit.cjs` отличается от копии в `.claude/` (CRLF нормализуется) |
| `deployed-command-missing` | предупреждение | нет `.claude/` или нет развёрнутого файла: система не установлена, но это не порча знания. В дистрибутивной копии (хранилище — корень git, `.claude/` нет) не выдаётся |
| `undeployed-command-source` | предупреждение | в `.claude/` есть `mv-*`, у которого нет исходника в `Dist/`, обычно остаток старой версии |

`.claude/` ищется в двух местах (`findClaudeDir()`): внутри хранилища (самостоятельная раскладка) и уровнем выше (встроенная). Ссылки в развёрнутых командах проверяются как ссылки хранилища.

### Плагин `mv`: команды без копий

Для личной установки команды и хук не копируются в `.claude/`. Вместо этого ставится плагин Claude Code `mv`, а маркетплейс для него — само хранилище. Почему так решено — ниже, в «Почему так», раздел о спайке 2026-10-25.

| Файл | Что это | Откуда берётся |
|---|---|---|
| `.claude-plugin/marketplace.json` (корень хранилища) | маркетплейс `memovaleos` с одним плагином `mv`, источник `./Knowledge-OS/Dist/plugin` | генерирует [[Knowledge-OS/Tools/build-plugin.mjs]] |
| `Knowledge-OS/Dist/plugin/.claude-plugin/plugin.json` | манифест плагина | генерируется |
| `Knowledge-OS/Dist/plugin/commands/<имя>.md` | обёртка для каждой `Dist/commands/mv-<имя>.md`: описание, подсказка аргументов, `allowed-tools` исходника плюс `Glob` и `Read`. Тело только находит хранилище и велит выполнить исходник | генерируется |
| `Knowledge-OS/Dist/plugin/hooks/hooks.json` | хук `PreToolUse` на `Read\|Grep\|Glob`, exec-форма: `node ${CLAUDE_PLUGIN_ROOT}/hooks/budget-audit-runner.cjs` | генерируется |
| `Knowledge-OS/Dist/plugin/hooks/budget-audit-runner.cjs` | находит хранилище под `CLAUDE_PROJECT_DIR` и выполняет его `Dist/hooks/budget-audit.cjs` в том же процессе (`require`) | пишется руками |

**Ни одной копии текста.** Обёртка не пересказывает команду: она читает `<хранилище>/Knowledge-OS/Dist/commands/mv-<имя>.md` и выполняет прочитанное. Правка команды доходит до каждой установки плагина, как только она есть в хранилище, и обновлять плагин не нужно. Из исходника копируется только то, что Claude Code читает раньше текста: `description`, `argument-hint` и `allowed-tools`. Эти копии генерирует `build-plugin.mjs`, а `--check` падает, если они устарели. Тест `build-plugin.test.mjs` запускает `--check`, так что правка исходника без пересборки роняет `npm test`.

**Имена.** Команды плагина Claude Code регистрирует только с пространством имён, так что `mv-check.md` становится командой плагина `check` и вызывается как `/mv:check` (выбор владельца 2026-10-25). Командная установка копирует те же исходники и оставляет `/mv-check`. Тексты команд называют себя `/mv-…`, и обёртка говорит ассистенту, что в плагине это `/mv:…`.

**Поиск хранилища.** И обёртка, и запуск хука ищут его одинаково: сам корень проекта, если он и есть хранилище, иначе `MemoValeOS/`, иначе первый прямой подкаталог, где есть и `Knowledge-OS/`, и `Project-OS/`. В спайке путь к `MemoValeOS/` был вписан в `hooks.json`, и хранилище под другим именем не писало бы журнал.

```bash
node "Knowledge-OS/Tools/build-plugin.mjs"           # пересобрать после правки Dist/commands/
node "Knowledge-OS/Tools/build-plugin.mjs" --check   # 1, если плагин устарел
```

Установка — две команды Claude Code, обе в local scope (их печатает план `adopt.mjs --local`, а выполняет владелец):

```bash
claude plugin marketplace add ./MemoValeOS --scope local
claude plugin install mv@memovaleos --scope local
```

## Почему так

- **Почему две копии.** Транспорт (патч путей манифеста) видит только хранилище, а загрузчик (Claude Code) — только `.claude/` проекта. Записанное решение (os-v3) — принять две копии как цену и сделать их расхождение ошибкой валидатора, а не полагаться на внимательность.
- **Почему план по умолчанию.** Установщик, который пишет до того, как его попросили, нельзя показать человеку до применения (`INST-9` в [[QA]]). Команда `/mv-adopt` передаёт план дословно, а не пересказом: «человек решает по этому списку, а пересказ — не список».
- **Почему одобрение по классам.** `settings` и `claude-md` меняют файлы, которые проекту уже принадлежат, а остальные классы лишь добавляют новые. Риск разный, и одобрение одного класса не распространяется на следующий.
- **Почему не `~/.claude/commands/`.** Пользовательская копия видна во всех проектах и расходится с репозиторием при первой правке. В проекте-носителе такая копия `/mv-close` месяц описывала ритуал из трёх вопросов, которого уже не было. Расхождение нашлось, только когда её прочли как авторитетную.

### Плагин Claude Code для личной установки: спайк 2026-10-25

Решение владельца по плану универсальной установки: личную установку (`--local`) делать плагином Claude Code, а не копированием в `.claude/`, если проверка это подтвердит. Проверка проведена на Claude Code 2.1.310, Windows, на временном git-хосте: отслеживаемый `CLAUDE.md` команды, копия хранилища в `MemoValeOS/`, исключённая через `.git/info/exclude`. Скрипт сборки плагина лежит в проекте-носителе путём `Plans/25.10.2026/plugin-spike-build.mjs`. После проверки плагин, маркетплейс, кэш и временный хост удалены, а глобальное состояние сверено с исходным.

**Как был устроен плагин.**
- Маркетплейс — `.claude-plugin/marketplace.json` в корне хранилища, сам плагин — `Knowledge-OS/Dist/plugin/` (источник `./Knowledge-OS/Dist/plugin`). Источник маркетплейса — локальный каталог, без сети.
- Одиннадцать команд плагина — тонкие обёртки. Каждая читает `${CLAUDE_PROJECT_DIR}/MemoValeOS/Knowledge-OS/Dist/commands/mv-*.md` и выполняет прочитанное. Текст команды живёт только в хранилище, поэтому копий нет и расходиться нечему.
- Хук плагина запускает исходник хранилища: `node ${CLAUDE_PROJECT_DIR}/MemoValeOS/Knowledge-OS/Dist/hooks/budget-audit.cjs`.
- `claude plugin validate` принял и маркетплейс, и плагин, с двумя необязательными предупреждениями: нет описания маркетплейса и нет иконки.

**Что подтвердилось.**
- `claude plugin marketplace add ./MemoValeOS --scope local` и `claude plugin install memovaleos@… --scope local` не меняют `~/.claude/settings.json` (хеш до и после совпал). Оба объявления ложатся в `.claude/settings.local.json` проекта.
- `${CLAUDE_PROJECT_DIR}` подставляется в текст команды плагина. Команда прочитала канонический текст из хранилища и запустила `mv.cjs validate-vault` без запроса разрешения: `allowed-tools` команды плагина действуют.
- Хук плагина пишет журнал, путь в нём считается от корня проекта.
- Постоянная цена в контексте — около 483 токенов на описания одиннадцати команд (`claude plugin details`), примерно столько же, сколько у скопированных команд. Вызов — около 230 токенов на обёртку.
- `plugin uninstall` и `marketplace remove` снимают объявления.

**Что спайк показал сверх ожиданий — это вводные для этапа 2.**
- **Имена.** Команды плагина регистрируются только с пространством имён: `/memovaleos:mv-check`. Голого `/mv-check` в списке команд сессии нет, и в безголовом режиме (`claude -p`) он не раскрылся. Работает ли голое имя в интерактивной сессии, не проверено. Ритуал, документация и привычка говорят `/mv-*`, так что имя — решение этапа 2.
- **След вне проекта есть, хотя и не в настройках.** Claude Code ведёт учёт в `~/.claude/plugins/` (`installed_plugins.json`, `known_marketplaces.json`, `cache/`, `data/`), даже при local scope. При первой записи `settings.local.json` он создал глобальный `~/.config/git/ignore` со строкой `**/.claude/settings.local.json`. Поэтому `git status` хоста был пуст — его скрыл глобальный файл, а не установка.
- **Исключения всё равно нужны.** Хук пишет `.claude/budget-audit.jsonl` в корень проекта, и `git status` показал `?? .claude/`. Личной установке по-прежнему нужен класс `exclude` — для каталога хранилища и артефактов бюджета, — но уже без команд, хука и настроек.
- **Имя папки хранилища зашито** в путь хука и в первый шаг обёрток (`MemoValeOS/`). Обёртки умеют искать хранилище через Glob, а хук нет: ему нужен поиск или параметр установки.
- **Удаление оставляет следы.** После удаления `settings.local.json` остаётся с пустыми `enabledPlugins` и `extraKnownMarketplaces`, а кэш плагина в `~/.claude/plugins/cache/` не удаляется.
- **Абсолютный путь.** Маркетплейс записан абсолютным путём к хранилищу, поэтому перенос хранилища ломает установку. Для local scope, которая живёт на одной машине, это приемлемо.

**Решение по спайку: годится.** Личная установка идёт плагином. Командная (`--team`) остаётся на копировании: плагин ставит каждый участник сам, и в облачных сессиях Claude Code локальные плагины не грузятся. Оба вопроса, которые спайк оставил открытыми, закрыты в том же этапе:
- **имена** — плагин называется `mv`, команды без префикса (`/mv:check`), это выбор владельца;
- **поиск хранилища хуком** — его делает `budget-audit-runner.cjs`, а не зашитый путь (раздел «Плагин `mv`» выше).

## Пример

План на проекте-носителе, где всё уже развёрнуто руками:

```text
Project root : C:\work\project
Vault        : C:\work\project\MemoValeOS  (os-v4)

  CLAUDE.md              present, 4 lines, no redirect
  .claude/commands/      present, 11 file(s) — 11 ours, 0 the project's
  .claude/hooks/         present, 2 file(s) — 2 ours, 0 the project's
  .claude/agents/        absent
  .claude/settings.json  present, valid JSON, 1 PreToolUse matcher(s)

1 change(s) proposed:

  [claude-md] mark CLAUDE.md  — redirect already correct; markers added

Unchanged:

  [commands] .claude\commands\mv-adopt.md  — already identical
  …
  [settings] .claude\settings.json  — the budget hook entry is already current
  [gitignore] .gitignore  — already ignores the budget artifacts

This was a plan; nothing was written. Re-run with --apply to carry it out.
```

`--verify` на этом же проекте печатает `OK — every deployable file matches its source in Knowledge-OS/Dist.`: `mark` не считается расхождением исходника и копии.

Сценарий с чужим `CLAUDE.md` (`INST-10` в [[QA]]): у проекта есть свои `.claude/agents/`, `.claude/commands/deploy.md` и `CLAUDE.md`. После `--apply` файлы `agents/` и `deploy.md` байт в байт прежние. В `CLAUDE.md` сверху появился блок в маркерах, а прежнее содержимое целиком лежит в `Project-OS/Inbox/Adopted CLAUDE.md`. Повторный `--apply` печатает `Nothing to change` (`INST-12`).

## Подводные камни

- **Править нужно `Dist/`, а не `.claude/`.** Затем `adopt.mjs --apply --only commands` (или `--yes`, если копия уже разошлась).
- **Перепись считает «нашими» хуки по префиксу `budget-audit`.** Если в `.claude/hooks/` лежит и устаревшая копия теста, она тоже засчитается как наша.
- **Наша запись в `settings` узнаётся по подстроке `budget-audit.`** в JSON записи хука. Чужой хук, в команде которого случайно встретится это имя, будет принят за наш и при `replace` заменён.
- **Exec-форма нужна свежему Claude Code.** Версия, которая поле `args` не знает, запустит голый `node` с JSON на stdin. Это ошибка без блокировки: хук молчит, но работе не мешает.
- **Удаление без записи установки** (установки до 2026-10-26) узнаёт наше только по совпадению с текущим `Dist/`. Копия старой версии, например `budget-audit.mjs`, тогда отказывает, и её снимают с `--yes`.
- **Командная установка, переведённая на личную**, оставляет копии `/mv-*` рядом с плагином `/mv:*`. План `--local` об этом предупреждает; снять копии — `--uninstall --team`, когда плагин заработал. Так же план называет `CLAUDE.local.md`, если тот указывает на хранилище: это ручная личная установка образца 2026-10, файл rules её заменяет.
- **Личная установка живёт в одном рабочем дереве.** Хранилище и файл rules не отслеживаются, поэтому в другие worktree того же репозитория они не попадают. `info/exclude` у всех worktree один: `--git-path` ведёт в `.git` основного репозитория, так что блок исключений общий. На Linux и macOS плагин включён и в других worktree, потому что его запись лежит в `settings.local.json` основного checkout. Но хранилища там нет: обёртка команды его не находит, а хук молча выходит с кодом 0. Работать с ОС нужно в том дереве, где лежит хранилище. Командная установка отслеживается git и есть в каждом worktree. Тест: «--local in a linked worktree excludes through the main repository and leaves both trees clean».
- **Сессия, запущенная из пакета, видит только его поддерево.** Если хранилище лежит в корне репозитория, а Claude запускают в `packages/api/`, ассистенту без `--add-dir` недоступно само хранилище. Хранилище кладут в ту папку, где запускают Claude, или запускают Claude там, где лежит хранилище.

## Как менять

- **Новый разворачиваемый файл.** Положите исходник в `Dist/`. Если это новый класс, добавьте его в `ALL_CLASSES`, напишите функции `plan*()` и `apply*()`, обновите перепись. Если это новый файл существующего класса, ничего менять не нужно: фильтр подхватит его сам.
- **Тесты** — [[Knowledge-OS/Tools/adopt.test.mjs]]: план не пишет, чужое не трогается, нечитаемые настройки не переписываются, повтор ничего не меняет; отдельно — linked worktree, пакет монорепо в обоих режимах и checkout с CRLF.
- **Правило расхождения** для нового файла — в `validate-vault.mjs`, рядом с `deployed-command-drift`.
- **Документация** — [[Knowledge-OS/Protocols/Deployment-Protocol]], раздел установки в README.md, тесты `INST-*` в [[QA]] и эта страница.

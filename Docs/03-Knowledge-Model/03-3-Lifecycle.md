# 03-3. Жизненный цикл знания

> **Описывает:** [[Knowledge-OS/Schema/Knowledge-Lifecycle]], ключ `lifecycles` в [[Knowledge-OS/Schema/schema.json]], раздел Lifecycle Review в [[Knowledge-OS/Protocols/Knowledge-Maintenance-Protocol]], правила валидатора, которые держат `lifecycle` честным, в [[Knowledge-OS/Tools/validate-vault.mjs]].
> **Связано:** [[Docs/03-Knowledge-Model/03-2-Metadata-and-Status]] — чем `lifecycle` отличается от `status`, [[Docs/03-Knowledge-Model/03-4-Evidence]] — пороги, без которых нет `active`, [[Docs/03-Knowledge-Model/03-6-Uncertainty-Ledger]] — блокирующие неопределённости держат знание в `draft`, [[Docs/05-Project-OS/05-4-Session-Lifecycle]] — где в ритуале закрытия происходит повышение, [[Docs/04-Assistant-Behaviour/04-4-Protocols]] — протоколы Promotion и Maintenance.

## Назначение

`lifecycle` отвечает на один вопрос: **можно ли этому знанию доверять как текущему?** Это центральное различие всей системы. Без него пустой заголовок, набросок по догадке и выстраданная архитектурная истина выглядят для следующей сессии одинаково — как текст в файле. С ним черновик заметно отличается от утверждённого: только `active` считается знанием проекта, а чтобы стать `active`, заметка должна пройти порог доказательности, не иметь открытых блокирующих вопросов и, для части типов, получить принятие человеком.

## Как работает

### Состояния и переходы

| Состояние | Смысл | Как используется |
|---|---|---|
| `draft` | знание создаётся или уточняется | читать можно, опираться нельзя |
| `active` | текущее и авторитетное | единственное, что считается знанием проекта |
| `superseded` | заменено более новым | не должно перекрывать замену |
| `archived` | хранится ради истории | по умолчанию не используется |

```mermaid
stateDiagram-v2
    [*] --> draft: новая заметка
    draft --> active: порог evidence + нет inferred/unknown + нет open blocking + принятие
    active --> superseded: появилась замена (supersedes::)
    active --> archived: хранится только для истории
    superseded --> archived
    [*] --> active: Finding (рождается active)
```

Правила Knowledge-Lifecycle:

- новое знание начинается с `draft`, если его состояние не установлено заранее;
- только `active` — текущее знание;
- `superseded` не перекрывает свою замену;
- `archived` по умолчанию не используется;
- смена `lifecycle` не должна молча менять содержание.

### Как пользоваться черновиком

`draft` читать можно — он говорит, что проект *думает* на данный момент. Но:

- его нельзя цитировать как факт проекта и нельзя строить на нём Decision;
- если работа зависит от чернового утверждения — проверить его до уровня, нужного типу, или записать неопределённость;
- при расхождении черновика с репозиторием прав репозиторий.

Свежеинициализированный Project-OS целиком `draft`. Это правильное стартовое состояние: каркас — не знание, пустой раздел — не факт о проекте.

### Условия повышения `draft → active`

[[Knowledge-OS/Protocols/Knowledge-Maintenance-Protocol]], §4, требует всех четырёх:

1. заметка достигает порога доказательности своего типа (`evidenceFloorByType`);
2. в ней не осталось утверждений со статусом `inferred` или `unknown`;
3. на неё не ссылается открытая блокирующая неопределённость;
4. владелец принял её как текущую.

Кто может выполнить переход:

| Тип | Кто повышает |
|---|---|
| `research` со `status: completed`, `log`, `resource` | Claude сам |
| `task`, `epic` при `status: done` | Claude **обязан**, в той же правке |
| `product`, `architecture`, `decision` | только с явного принятия человеком |
| остальные | Claude предлагает |
| `finding` | рождается `active`, перехода нет |

Перевод в `superseded` — когда есть замена (на замене пишется `supersedes:: [[...]]`), в `archived` — когда заметка нужна только для истории.

### Ритм пересмотра

При каждом прогоне протокола обслуживания пересматриваются все `draft`-заметки типов `product`, `architecture`, `decision`, `research` старше 14 дней по `created`: изменились ли порог, блокирующие вопросы, содержание. Нет изменений — нет действий: перепроверка не переписывание.

### Что проверяет машина

| Нарушение | Правило | Уровень |
|---|---|---|
| значение не из `lifecycles` | `unknown-lifecycle` | ошибка |
| `active` без `evidence` (кроме метатипов) | `missing-evidence-for-active` | ошибка |
| `active` ниже порога типа | `below-evidence-floor` | ошибка |
| `active`, но в теле только заголовки | `active-scaffold` | ошибка |
| `draft`, и в теле только заголовки | `scaffold` | предупреждение |
| открытая блокирующая неопределённость ссылается на `active` | `blocking-uncertainty-on-active` | ошибка |
| Task `done`, Epic `active`/`done`, Decision `accepted` — но `draft` (`activeLifecycleStatuses`) | `lifecycle-behind-status` | ошибка |
| все задачи эпика `done`/`cancelled`, а эпик нет | `epic-status-behind-tasks` | ошибка |
| эпик `done`, а задачи нет | `epic-status-ahead-of-tasks` | ошибка |
| `active` с изменившимся `source` | `stale-source` | предупреждение |

«Скелет» определяет `isScaffold()`: после удаления пустых строк, заголовков, строк-цитат (`>`), горизонтальных линеек и пустых маркеров списка не остаётся ничего.

За пределами валидатора `lifecycle` читают ещё двое. Представления `.base` в [[Knowledge-OS/Knowledge-DB.base]] — по одному на каждое состояние плюс «Schema violations». Провайдер контекста не отдаёт `superseded` и `archived` в текущий контекст вовсе, а `draft` отдаёт с предупреждением (см. [[Docs/06-Tooling/06-5-Context-Provider]]).

## Почему так

**Lifecycle отделён от status.** Рабочее состояние и доверие — разные оси. Задача может быть `in-progress`, а знание о ней — черновым. Одно поле на оба вопроса вынуждало бы врать в одном из них. Но у типа без собственного рабочего цикла второе поле ничего не добавляет: у `product` и `architecture` словарь `status` повторял `lifecycle`, поля расходились, и с os-v5 у них есть только `lifecycle`.

**Скелет не может быть `active`.** Именно так тихий дрейф и начинается: заметка-заготовка с правильным frontmatter выглядит как знание. `active-scaffold` делает это невозможным, а предупреждение `scaffold` на черновиках напоминает, что заготовка ещё пуста.

**Task и Epic повышаются автоматически и обязательно.** Это урок, оплаченный дважды. Задачи T11 и T12 в проекте-носителе Archi закрылись со `status: done`, но `lifecycle: draft`, а T12 — вовсе без `evidence`, `created`, `updated`. Ничто этого не ловило: порог применяется только к `active`, а задача осталась `draft`. Нашли ручным сравнением соседних задач. Тогда в схему добавили порог `task: L2`, а в валидатор — правило о `lifecycle` закрытой задачи: одного порога было мало, он не видел именно те случаи, ради которых заводился. С эпиками вышло тоньше: эпики E02 и E03 отстали по `status` от своих задач (поймало `epic-status-behind-tasks`), а E06 стоял `status: active, lifecycle: draft`. Черновой эпик не виден правилу `blocking-uncertainty-on-active` — оно проверяет только `active`-цели, — так что устаревшее поле выключает гейт. Появилось второе правило, для эпиков. Третий раз класс вернулся на решениях: ADR-003/004/005 стояли `accepted` + `draft`, а правила для `decision` не было. С os-v5 это одно правило `lifecycle-behind-status`, а закрепляющие статусы — данные `activeLifecycleStatuses`.

**Product/Architecture/Decision — только с человеком.** Это три типа, где ошибка дороже всего и где «доказательство» — это либо слово владельца (`product`), либо его выбор (`decision`), либо структура, на которую опирается всё остальное (`architecture`). Автоматическое повышение здесь — это ИИ, утверждающий собственные выводы.

**Finding рождается `active`.** Ему нечего ждать: это не вывод, который созреет, а зафиксированное наблюдение. Держать его в `draft` значило бы держать в `draft` навсегда.

## Пример

Закрытие задачи в ритуале. До:

```yaml
---
type: task
status: in-progress
lifecycle: draft
created: 2026-09-12
---
```

После того как работа слита и проверена:

```yaml
---
type: task
status: done
lifecycle: active
evidence: L2
created: 2026-09-12
updated: 2026-09-15
source:
  - path: src/graph/builder.ts
    commit: "a1b2c3d"
---
```

Если выставить только `status: done` и забыть остальное, валидатор скажет:

```text
[lifecycle-behind-status] task is `done` but `lifecycle` is still `draft`, so neither the evidence floor nor blocking-uncertainty-on-active applies to it
```

А если наоборот — поставить `lifecycle: active`, но забыть `evidence`, — `missing-evidence-for-active`; при `evidence: L1` — `below-evidence-floor` (`task` требует `L2`).

Замена архитектурной заметки: новая заметка `Graph-Model-v2` становится `active` и несёт строку `supersedes:: [[Graph-Model]]`, старая переводится в `lifecycle: superseded`.

## Подводные камни

- **Переходы не проверяются.** Валидатор видит только текущее значение, истории у него нет. `active → draft` или `archived → active` пройдут молча.
- **Принятие человеком не машинное.** Условия 2 и 4 повышения (нет `inferred`/`unknown`, есть принятие) исполняются только дисциплиной. `decision` с `lifecycle: active` и `evidence: L2` пройдёт валидатор независимо от того, принимал ли его кто-нибудь.
- **`superseded` без `supersedes::` никто не ловит**, и наоборот — `supersedes::` на заметку, оставшуюся `active`.
- **Скелетность считается грубо.** Строка таблицы, одиночная ссылка или комментарий `<!-- -->` считаются содержанием, так что заметка из заголовков плюс HTML-комментария не будет скелетом.
- **Черновой эпик выключает гейт неопределённостей для самого себя — и только.** Правило `blocking-uncertainty-on-active` не спускается от эпика к его задачам: оно проверяет только заметки, на которые ссылается строка реестра. Раньше ритуал закрытия и комментарии валидатора называли это «всё поддерево»; теперь [[Project-OS/06-AI/AI]] говорит, как есть, и советует ссылаться в строке на задачи, которые она блокирует. См. [[Docs/03-Knowledge-Model/03-6-Uncertainty-Ledger]].
- **Ритм 14 дней ничем не исполняется.** Это шаг протокола обслуживания, а не проверка.

## Как менять

- **Новое состояние жизненного цикла** — в `lifecycles` в [[Knowledge-OS/Schema/schema.json]] и описание в [[Knowledge-OS/Schema/Knowledge-Lifecycle]] (состояние, переходы, правила). Затем найти в коде все сравнения с литералами `"active"`, `"draft"`, `"superseded"`, `"archived"`: валидатор (`missing-evidence-for-active`, пороги, `stale-source`, правила задач и эпиков), провайдер контекста (что отдавать, что пропускать), представления в [[Knowledge-OS/Knowledge-DB.base]]. Схема даёт словарь, но смысл состояний зашит в эти места.
- **Новый закрепляющий статус** («status X требует lifecycle не `draft`») — строка в `activeLifecycleStatuses` в [[Knowledge-OS/Schema/schema.json]], а не новое правило. `loadSchema()` проверит, что статус есть у типа. Нужна позитивная фикстура по образцу `lifecycle-behind-status-decision` и, если тип новый для правила, строка в негативной `lifecycle-behind-status-clean` (см. [[Docs/06-Tooling/06-6-Tests-and-Fixtures]]).
- **Изменение того, кто может повышать,** — правка [[Knowledge-OS/Protocols/Knowledge-Maintenance-Protocol]] §4 и, если затрагивает ритуал закрытия, [[Project-OS/06-AI/AI]] вместе с `/mv-close` (две копии команды должны совпадать — `deployed-command-drift`).
- Запись в [[CHANGELOG]] обязательна, если существующие заметки начнут падать.

# 03-5. Связи и ссылки

> **Описывает:** [[Knowledge-OS/Schema/Relationship-Types]], [[Knowledge-OS/Rules/Linking-Rules]], ключ `relationshipTypes` в [[Knowledge-OS/Schema/schema.json]], разрешение ссылок и проверки связей в [[Knowledge-OS/Tools/validate-vault.mjs]].
> **Связано:** [[Docs/04-Assistant-Behaviour/04-4-Protocols]] — Relationship-Discovery-Protocol, [[Docs/04-Assistant-Behaviour/04-3-Context-Selection]] — почему связь не означает загрузку, [[Docs/06-Tooling/06-2-Stale-Check-and-Graph-Report]] — связность графа целиком, [[Docs/09-Obsidian-Integration]] — Dataview как читатель полей, [[Docs/05-Project-OS/05-2-Delivery-Model]] — `contains::` между Epic и Task.

## Назначение

Знание связано: задача реализует эпик, решение ограничивает архитектуру, исследование поддерживает решение. Система различает два вида связей:

- **обычная ссылка** `[[Target]]` — навигация. Она не утверждает никакого отношения;
- **типизированная связь** `relationship-type:: [[Target]]` — утверждение о направленном смысловом отношении из закрытого словаря.

И одно правило, на котором держится вся модель контекста: **связь не означает, что цель нужно загрузить.** Ссылка говорит, где искать, если понадобится, а не что читать.

## Как работает

### Словарь

| Тип | Смысл: источник → цель |
|---|---|
| `contains` | содержит (Epic → Task) |
| `depends-on` | требует |
| `implements` | реализует |
| `constrained-by` | ограничен |
| `supports` | даёт свидетельство или поддержку |
| `affects` | меняет или влияет |
| `based-on` | выведен из |
| `supersedes` | заменяет |
| `related-to` | осмысленно связан, когда сильнее нечего сказать |

Правила: брать самый конкретный тип; сохранять направление; не заводить новые типы ради случая; `related-to` — только если ничего конкретнее не подходит; связь должна быть осмысленной.

### Запись

Связь — inline-поле в теле, не во frontmatter:

```markdown
## Related

depends-on:: [[Core-Engine]]
constrained-by:: [[ADR-003 Plugin Isolation]]
constrained-by:: [[ADR-001-Git-Branching-Model]]
```

- имя поля — тип из словаря;
- поле стоит в разделе, к которому относится, или под `## Related`;
- связь записывается на источнике и указывает на цель;
- несколько целей одного типа — повтор поля.

Ссылка внутри поля остаётся обычной wikilink: граф, обратные ссылки и валидатор видят её без всяких плагинов. Запросить её *как типизированное поле* может только Dataview. Bases читает только YAML-frontmatter, а связи во frontmatter запрещены — значит, без Dataview связь записана и проверена, но спросить о ней нельзя.

### Запросы (Dataview)

Прямой — на что указывает сущность:

```text
TABLE WITHOUT ID file.link AS entity, depends-on
FROM "Project-OS"
WHERE depends-on
```

Обратный — что указывает на сущность:

```text
LIST FROM "Project-OS"
WHERE contains(depends-on, link("Core Engine"))
```

Дефис в имени поля экранировать не нужно; повторённое поле читается как список (`length(contains)` считает цели). Запрос возвращает то, что записано, а не то, что правда.

### Разрешение ссылок

Валидатор разрешает ссылки так же, как Obsidian, но только среди файлов, которыми хранилище владеет (`isVaultOwned()`: `Knowledge-OS/`, `Project-OS/`, `Metrics/`, `Plans/`, `Archive/`, `Docs/` и файлы в корне хранилища).

1. `collectLinks()` вынимает цели `[[...]]`, отбрасывая алиас `|...` и якорь `#...`/`^...`. Перед этим `stripCodeAndInline()` удаляет блоки кода и inline-код: ссылки-примеры там не считаются.
2. `linkResolves()`: ссылка **с** `/` разрешена, если есть файл с точно таким путём (с `.md` или без) или, при его отсутствии, файл, чей путь оканчивается на `/<цель>` (`pathLinkCandidates()`; так Obsidian разрешает частичный путь). Отката на одно имя файла нет: `[[Wrong/Folder/Note]]` не разрешится, даже если где-то есть `Note.md`. Ссылка **без** `/` разрешена, если basename совпадает хотя бы с одной `.md`-заметкой.
3. Не разрешилась — `broken-link` (ошибка).
4. `ambiguousBareLink()`: ссылка без `/` совпадает по basename с несколькими заметками, или частичный путь совпадает с концом путей нескольких файлов — `ambiguous-basename-link` (ошибка). Точный полный путь неоднозначным не бывает.

Индекс basename строится только по `.md` (ссылка без пути на не-заметку в Obsidian не разрешается), и только по файлам хранилища — чужой `Architecture.md` в дереве проекта не делает неоднозначной законную ссылку `[[Architecture]]`.

Где проверяются ссылки:

| Где | Проверяется | Почему так |
|---|---|---|
| файлы хранилища, кроме папок `Archive` и `Inbox` | да | `Archive` — история, `Inbox` — чужой `CLAUDE.md`, его ссылки ведут в чужой граф (`LINK_EXEMPT`) |
| `Docs/` | да | документация, которая молча указывает на переименованный инструмент, хуже отсутствующей |
| `.claude/commands/mv-*.md` | да | развёрнутые команды ссылаются в хранилище (например, на шаблон Finding) |
| остальное в `.claude/`, чужие деревья | нет | хранилище им не судья |

### Проверка типизированных полей

`collectInlineFields()` находит строки, начинающиеся с `name::` или с пункта списка `- name::` (`*` и `+` тоже), в теле **управляемых** заметок (код вырезан). Имя не из `relationshipTypes` — `unknown-relationship-field`. Это ловит самую тихую поломку: опечатку `depend-on::`. Ссылка разрешается, заметка отображается, граф рисует ребро — ничего не выглядит сломанным. Пропадает только сама связь: ни один запрос по типу её больше не вернёт.

### Кто ещё читает связи

- `contains::` в эпике (в начале строки или пункта списка) — источник для `epic-status-behind-tasks` / `epic-status-ahead-of-tasks`: статусы задач, на которые указывают строки `contains::`, сравниваются со статусом эпика.
- Все ссылки (не только типизированные) из owned-файлов — источник для `orphaned-note`: non-meta заметка в `Project-OS/`, на которую не ссылается ни один другой owned-файл, — предупреждение. Ссылка без пути считается ведущей на *все* заметки с этим basename — переоценка входящих ссылок здесь безопасное направление. Ссылка с путём разрешается по тому же правилу, что и в `linkResolves()`, — `resolveLinkTargets()` и `linkResolves()` больше не расходятся.
- `Tools/graph-report.mjs` — связность графа целиком и доля типизированных рёбер, см. [[Docs/06-Tooling/06-2-Stale-Check-and-Graph-Report]].

## Почему так

**Не во frontmatter.** Связь живёт в контексте раздела, который её объясняет. Во frontmatter она превратилась бы в список ключей без объяснения, а схема метаданных разрослась бы ключом на каждый тип связи. Inline-поле — одновременно обычная ссылка (работает без плагинов) и поле (работает с Dataview).

**Связь ≠ загрузка.** Если бы каждая ссылка была требованием к контексту, ассистент шёл бы по графу рекурсивно и грузил половину хранилища на каждую задачу. Это ровно то, против чего построена система. Linking-Rules: «не следовать по ссылкам рекурсивно без причины, связанной с задачей».

**Неоднозначность — ошибка.** Однажды в хранилище оказались два файла «Context Index», и ссылка открывала тот, который выбрал Obsidian, а не тот, что имел в виду автор. Поскольку в системе есть законно одноимённые файлы (корневой `README.md` и `Knowledge-OS/README.md`, сущность и её пустой шаблон), правило — ссылаться по полному пути.

**Разрешение по реальной цели.** Раньше блокирующая неопределённость сравнивалась с *каждой* заметкой того же basename, и активная заметка-тёзка давала ложную ошибку. `resolveLinkTargets()` разрешает ссылку ровно так, как Obsidian, — фикстура `blocking-uncertainty-basename-collision` держит регрессию. Позже то же правило распространили на ссылки с путём: раньше `linkResolves()` при промахе по пути откатывался на basename, и ссылка в несуществующую папку считалась рабочей (фикстура `path-link-wrong-folder`).

**Только своё.** На установке в проект с собственным memory bank валидатор выдал два десятка `broken-link`, ни одна из которых не была правдой: ссылки вели в граф, которого хранилищу не показывали. Область проверки сузили до своего (фикстура `foreign-tree`).

## Пример

Эпик с задачами:

```markdown
## Tasks

contains:: [[T13-Import-Analyzer]]
contains:: [[T14-Function-Analyzer]]
```

Если обе задачи `done`, а эпик `active`:

```text
[epic-status-behind-tasks] all 2 contained Tasks are done/cancelled but the Epic is still `active`
```

Опечатка в поле:

```markdown
depend-on:: [[Core-Engine]]
```

```text
[unknown-relationship-field] inline field `depend-on::` is not a relationship type defined by Relationship Types
```

Неоднозначная ссылка `[[README]]` при наличии `README.md` и `Knowledge-OS/README.md`:

```text
[ambiguous-basename-link] link `[[README]]` matches 2 files (README.md, Knowledge-OS\README.md); use the full path
```

## Подводные камни

- **Раньше поле в пункте списка не проверялось.** Регулярное выражение требовало имени в начале строки, и `- depends-on:: [[X]]` (Dataview такое читает) проходил мимо `unknown-relationship-field`, а `- contains:: [[T01]]` не попадал в расчёт статуса эпика. Теперь обе формы равноправны — в валидаторе и в `graph-report.mjs` (фикстура `list-item-relationship-field`).
- **Раньше запросы в Relationship-Types использовали `FROM "Project OS"`** — старое имя с пробелом, и в таком виде возвращали пусто. Теперь там `FROM "Project-OS"`; при переименовании папок такие строки в прозе никто, кроме человека, не найдёт.
- **Типизированные поля проверяются только в управляемых заметках.** В `README.md`, `Docs/` и шаблонах опечатку не поймают.
- **Направление и смысл не проверяются.** `contains:: [[Epic]]` на задаче валиден, хотя направление обратное.
- **В `Docs/` можно ссылаться только на то, что есть в апстриме.** Валидатор проверит разрешимость в текущем хранилище, но ссылка на заметку проекта-носителя разрешится здесь и сломается после доставки.
- **`orphaned-note` переоценивает входящие ссылки** через голый basename: заметка-тёзка «спасает» сироту. Ссылки из чужих деревьев под хранилищем не считаются.

## Как менять

- **Новый тип связи** — значение в `relationshipTypes` в [[Knowledge-OS/Schema/schema.json]] и строка с направлением и смыслом в [[Knowledge-OS/Schema/Relationship-Types]]. Валидатор подхватит его без правки кода. Если тип нужен тип-специфичному правилу (как `contains` для эпиков), правило пишется в валидаторе отдельно.
- **Изменение области проверки ссылок** — `VAULT_OWNED_ROOTS`, `LINK_EXEMPT` в валидаторе; любое расширение должно сопровождаться фикстурой (образец — `docs-broken-link` / `docs-link-target`) и строкой в [[CHANGELOG]], потому что проекты с одноимённой папкой начнут получать ошибки.
- Подробности кода — [[Docs/06-Tooling/06-1-Validator]], тесты — [[Docs/06-Tooling/06-6-Tests-and-Fixtures]].

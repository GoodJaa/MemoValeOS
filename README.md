# MemoValeOS

Операционная система для проектного знания, рассчитанная на работу с ИИ-ассистентом.

> Этот файл написан для людей. Он объясняет, что это за система и почему она устроена именно так.
> Ассистент его не читает — его точка входа `CLAUDE.md`.

---

## Проблема

Работа с ИИ-ассистентом над реальным проектом ломается двумя предсказуемыми способами.

**Он забывает.** Каждая сессия начинается с нуля. Вы заново объясняете архитектуру, заново обосновываете решения, принятые месяц назад, и смотрите, как ассистент повторно оспаривает выбор, который вы уже сделали.

**Он догадывается.** Когда знания не хватает, ассистент не останавливается — он выдаёт уверенную фразу. Следующая сессия принимает эту фразу за факт проекта, и ошибка тихо накапливается.

Обычная реакция — написать больше документации и загрузить её в контекст целиком. Это усугубляет обе проблемы. Большой контекст дорог, он хоронит те несколько фактов, которые действительно нужны, и всё равно не позволяет отличить проверенное утверждение от выдуманного.

## Идея

Знание — это не куча документов. Это структура с правилами: как оно записывается, как находится и насколько ему можно доверять.

Система состоит из двух слоёв.

**Knowledge OS** — *как* управлять знанием. Схемы того, что такое сущность знания, правила поведения ассистента, протоколы выполнения работы. Здесь нет ничего про конкретный проект — именно поэтому слой копируется в следующий проект без изменений.

**Project OS** — *что* знает конкретный проект. Продукт, архитектура, решения, исследования, открытые вопросы. Всё здесь специфично для одного проекта.

Под обоими слоями — репозиторий как свидетельство. Он фиксирует, что проект реально реализует, а это не всегда совпадает с тем, что считает база знаний.

## Почему это работает

**Контекст подтягивается задачей, а не грузится в ассистента.**

Вместо загрузки базы знаний ассистент отталкивается от текущей задачи и расширяется наружу ровно настолько, насколько нужно: задача → эпик → архитектура → решения → исследования → код. Перед чтением он объявляет, что именно ищет и что будет считаться достаточным. На этом останавливается.

Гипотеза, которую это должно давать: стоимость не растёт вместе с базой знаний — проект с тысячей заметок загружает не больше контекста, чем проект с пятьюдесятью, потому что релевантность определяет задача, а не размер архива.

Что показал замер в проекте, где система разрабатывается (Archi, 18 задач, сентябрь 2026), — честно и в обе стороны. Всё хранилище стоит около **7% среднего контекста сессии** — примерно пять тысяч токенов, и величина не выросла при удвоении базы. Это скромнее исходной формулировки и защитимее: при доле в 7% утверждение «контекст не растёт с базой» близко к тавтологии, потому что база и так занимает малую долю.

Побочное наблюдение пришлось исправить. Раньше здесь стояло «правила не читают, но соблюдают»: прибор не видел, чтобы `Knowledge-OS/` открывали. Но он считал только файловые инструменты, а сессии читали через `cat`, `sed` и `Get-Content`. Перемер того же проекта 2026-10-13 с разбором командной строки (17 задачных сессий): `Knowledge-OS/` открывали в 15 из 17 — от одного до шести файлов, а перечитывали почти никогда (1 повтор на 38 чтений). Знание проекта, наоборот, перечитывали в 38 % чтений, и журнал этого не показывал. Соблюдает ли ассистент правила благодаря чтению, не установлено: самое заметное соблюдение — модель ветвления — держит git-хук `pre-push` проекта. Что именно заставляет правила соблюдаться, остаётся открытым вопросом в `Backlog.md`.

**Черновик заметно отличается от утверждённого знания.**

У каждой заметки есть жизненный цикл: `draft`, `active`, `superseded`, `archived`. Актуальным считается только `active`. Заметка-каркас, которую никто не заполнил, не может выдать себя за установленный факт: чтобы её повысить, нужно пройти порог доказательности и получить принятие человеком.

Именно это останавливает тихий дрейф. Без этого пустой заголовок и выстраданная архитектурная истина выглядят для следующей сессии одинаково.

**Утверждения несут своё доказательство.**

Утверждения градуируются по тому, как они установлены: прочитан файл, наблюдался результат выполнения, увидено реальное поведение системы, подтверждено человеком. Разным типам знания нужен разный минимум — архитектурное утверждение не становится доказанным оттого, что где-то рядом прошёл тест.

**Неизвестное записывается, а не растворяется в формулировке.**

Когда что-то неизвестно, оно попадает в реестр неопределённостей, а не превращается в правдоподобную фразу. Неопределённость с пометкой «блокирующая» удерживает затронутое знание в состоянии `draft`, пока не будет разрешена по-настоящему. Это убивает самый дорогой паттерн в работе с ИИ: *готово, но вон ту часть надо бы потом проверить.*

**Правила проверяет программа, а не добрые намерения.**

`Knowledge-OS/Tools/validate-vault.mjs` сверяет хранилище с его собственной схемой: обязательные поля, допустимые значения, битые ссылки, заметки из одних заголовков, неопределённости, противоречащие знанию, на которое они ссылаются, эпик, чей статус разошёлся со статусами его задач. Запуск из корня хранилища (нужен только Node 18 или новее):

```
node "Knowledge-OS/Tools/validate-vault.mjs"
```

Часть проверок — **предупреждения, а не ошибки**, и это осознанно. Заметка, на которую никто не ссылается, или утверждение, чьё доказательство с тех пор изменилось, — это данные о состоянии знания, а не повод остановить работу. Гейт, который обычно красный, перестают читать.

Правило, которое только записано, — это пожелание. Правило, которое проверяет скрипт, — это правило.

## Что внутри

```
Knowledge-OS/          переиспользуемый слой — копируется в любой проект
  Schema/              что такое сущность: типы, метаданные, связи, жизненный цикл, доказательства
  Rules/               как обязан вести себя ассистент
  Protocols/           процедуры: выбор контекста, повышение знания, сопровождение
  Tools/               валидатор, развёртывание, метрики, отчёт по графу, проверка
                       протухания, провайдер контекста
  Dist/                исходники команд и хука, разворачиваемые в .claude/ проекта
  os-manifest          что именно составляет слой ОС и переносится в другой проект

Project-OS/            знание конкретного проекта
  00-Home              точка входа
  01-Product           что строим и зачем
  02-Architecture      как это устроено
  03-Development       эпики, задачи, релизы
  04-Research          находки и открытые неопределённости
  05-Decisions         принятые архитектурные решения
  06-AI                проектная надстройка для ассистента
  07-Resources         внешние источники

Docs/                  документация разработчика: как устроена каждая часть и почему

CLAUDE.md              точка входа для ассистента
```

Подробное устройство системы — для того, кто будет её развивать или писать подобную, — описано пораздельно в документации разработчика: [[Docs/00-Index]]. Ассистент её, как и этот файл, не читает.

## Запуск нового проекта

Склонируйте этот репозиторий — `Knowledge-OS/` и `Project-OS/` приезжают вместе с ним как обычные файлы. `Project-OS` — скелет, не привязанный ни к какому продукту: пустые разделы с короткой подсказкой, что в каждый из них писать.

Заполните заметки продукта. Остальное нарастает по мере того, как проект узнаёт новое.

## О честности

Смысл всего этого не в аккуратности. Смысл в том, чтобы ассистент, работающий с этим хранилищем, не мог сообщить вам то, чего проект никогда не устанавливал, — а когда он чего-то не знает, признать это должно быть структурно проще, чем угадать. Чтобы он, подражая человеческому "ходу мысли", использовал только те знания, которые необходимы в данный момент.

## Установка и подключение

Как развернуть эту систему и подключить к ней ИИ-ассистента.

> **История репозитория пересобрана в os-v5 (2026-10-13).** Репозиторий начинается одним коммитом с тегом `os-v5`; история версий до него — в `CHANGELOG.md`. Клон, сделанный раньше, не сольётся с новым `master`: склонируйте заново.

### Два пути доступа

Систему можно использовать двумя способами, и требования ниже относятся к разным путям:

- **Полный путь, через Obsidian** — визуальное хранилище, таблицы `.base`, поля связей через Dataview, доступ ассистента через MCP Connector. Требует Obsidian и два community-плагина из таблицы ниже.
- **Голый git clone** — `validate-vault.mjs` и слэш-команды работают без Obsidian вообще, нужен только Node.js 18 или новее. Команды при этом не появляются сами: их разворачивает в `.claude/` шаг 5 установки. Это путь, которым пользуется Claude Code сам по себе, без визуального интерфейса.

Оба пути читают одни и те же файлы; ни один не требует другого. Проверено удалением: на копии без `.obsidian/` и без `.base`-файлов валидатор, тесты и метрики отрабатывают полностью. Obsidian даёт представления `.base` и удобство чтения — не механику. Сами `.base` при этом не источник истины: тот же список открытых задач выводится grep'ом по статусам, и ритуал так и делает.

### Опциональное подключение внешних инструментов

MemoValeOS может служить долговечным источником проектного контекста для любого внешнего инструмента — оркестратора, агентной среды, CI-задачи. Для этого есть провайдер контекста с общим интерфейсом: внешний инструмент ведёт свою задачу и отвечает за свой результат, а MemoValeOS отдаёт только выбранные заметки — вместе с их `lifecycle`, `evidence`, git-ревизией и дайджестом содержимого. Контракт определяет MemoValeOS (`Knowledge-OS/Protocols/Context-Provider-Protocol` и `Knowledge-OS/Schema/Provider-Mapping`); новый потребитель подстраивается под него, а не дописывает в него свои поля.

Провайдер работает по обычным файлам и **не требует открытого Obsidian**. Из корня хранилища:

```text
node "Knowledge-OS/Tools/context-provider.mjs" \
  --project-root <корень-проекта> --vault-root <корень-хранилища>
```

Если хранилище и есть проект — как в клоне этого репозитория, — оба корня совпадают. Если хранилище лежит подпапкой проекта, `--vault-root` указывает на эту подпапку.

Вызывающая сторона передаёт JSON-запрос через stdin и получает один JSON-ответ. Операции: `capabilities`, `health`, `prepare_context`, `checkpoint`, `restore`, `propose_knowledge`. Точные формы запросов — в `context-provider.test.mjs`; для ручной проверки — `npm run test:context-provider`. Конкретную argv-команду записывает конфигурация потребителя, поэтому абсолютные пути одной машины в репозитории не хранятся.

> **До os-v4 провайдер назывался адаптером Closure:** `closure-provider.mjs` и `npm run test:closure-provider`. Конфигурацию, которая их вызывает, нужно перевести на новые имена — совместимой прослойки нет. Формат запросов и ответов не изменился (протокол `1.0`). Подробности — `CHANGELOG.md`, секция os-v4.

**Почему это не размывает идею системы.** Различие между черновиком и установленным знанием переходит границу, а не теряется на ней:

- заметки в `superseded` и `archived` в текущий контекст не попадают вовсе, а `draft` и `stale` отдаются с явным предупреждением — не молча как факт;
- каждый источник несёт `type`, `lifecycle`, `status`, `evidence`, git-ревизию и SHA-256, так что принятое решение отличимо от наброска на стороне получателя;
- бюджет чтения настоящий: провайдер идёт только по явно переданным точкам входа, а не тянет хранилище целиком; не поместившееся возвращается **поимённо**, и ответ помечается `degraded` — тихого `ok` при усечении не бывает;
- обязательные точки входа (`CLAUDE.md` и `Knowledge-OS/Protocols/Context-Selection-Protocol`) провайдер добавляет сам, то есть дисциплина чтения лежит на нём, а не на вызывающей стороне;
- записи он не делает физически: в `context-provider.mjs` нет ни одной операции записи. `managed_write` отклоняется, а предложение об обновлении знания приходит как `draft` и ждёт человека.

**Граница закреплена правилом, а не обещанием.** `Knowledge-OS/Rules/AI-Governance`, раздел `Must Not`: автоматическое принятие внешних предложений — изменение того, как знание становится истинным в этой системе, и требует явного Decision, а не правки кода.

MemoValeOS от провайдера не зависит: его не вызывают ни валидатор, ни метрики, ни команды, ни ритуалы. Ссылаются на него только его собственный тест, два скрипта в `package.json` и страницы `Docs/`, которые его описывают, — без провайдера они уходят вместе с ним, а остальная система работает так же.

### Требования

| Что | Зачем | Примечание |
|---|---|---|
| **Obsidian** ≥ 1.7.2 | сама база знаний | только десктоп: плагин MCP на мобильных не работает |
| Ядровые плагины `bases` и `properties` | таблицы `.base` и редактор frontmatter | включаются в настройках Obsidian |
| **Node.js** 18 или новее | валидатор, метрики, все инструменты | для Obsidian и Claude Desktop — системный, не через nvm/fnm/asdf (см. ниже) |
| `npm install` | **для работы не нужен**; только для `npm test` (`acorn` в тестах синтаксиса) | единственная зависимость инструментов, `js-yaml`, лежит в `Knowledge-OS/Tools/vendor/`. Тестам — разово, из корня хранилища: в клоне этого репозитория это его корень |
| **MCP Connector** (community-плагин) | доступ ассистента к хранилищу | нужен только для подключения ИИ |
| **Dataview** (community-плагин) | делает поля связей (`depends-on:: [[...]]`) запрашиваемыми | без него это просто синтаксис — ссылки работают, но как поле их никто не читает |

#### Про Node — частая ошибка

Obsidian и Claude Desktop запускаются не из вашей оболочки и **не видят Node, установленный через менеджеры версий** (nvm, fnm, asdf). Ставьте системный пакет: установщик с nodejs.org, `winget install OpenJS.NodeJS.LTS` или Homebrew на macOS.

Если Node проекта старше 18 (так бывает, когда его требует сам проект), ничего переключать не нужно. Инструменты и команды `/mv-*` запускаются через лаунчер `Knowledge-OS/Tools/mv.cjs`. Его читает любой `node`, а он сам находит Node 18+ в `PATH`, nvm или nvm-windows и запускает им инструмент. Проверка:

```
node "Knowledge-OS/Tools/mv.cjs" doctor
```

Строка `tools run on` называет Node, которым будут работать инструменты, и объясняет почему. Если подходящего нет, лаунчер перечислит найденные версии и скажет, что сделать. Указать бинарник явно можно переменной `MVOS_NODE`. Подробно — `Docs/06-Tooling/06-8-Launcher.md`.

### Установка

1. **Склонируйте репозиторий.** `Knowledge-OS/`, `Project-OS/` и `CLAUDE.md` приезжают сразу — это обычные файлы, ничего разворачивать не нужно.

   Обратите внимание: `.gitignore` исключает `.obsidian/plugins/`, поэтому после клонирования плагины придётся поставить заново — в репозитории хранится только список включённых, не их код.

2. **Включите плагины** — community-плагины MCP Connector и Dataview (Dataview нужен, только если поля связей должны быть запрашиваемыми), в ядровых — `bases` и `properties`. Templater системе не нужен.

3. **Зависимости ставить не нужно.** Инструментам нужен только Node 18 или новее: `js-yaml` лежит в `Knowledge-OS/Tools/vendor/`, поэтому установка работает и без доступа к npm, и с npm, который идёт со старым Node хоста. `npm install` понадобится, только чтобы запускать тесты самой системы (`npm test`), — из корня хранилища. Если хранилище встроено подпапкой в другой проект, корневой `package.json` проекта может объявить его npm workspace — тогда одной установки в корне проекта хватает и на хранилище.

4. **Проверьте результат.** Из корня хранилища:

   ```
   node "Knowledge-OS/Tools/mv.cjs" validate-vault
   ```

   Ожидается `OK — no schema violations`. Ненулевой код возврата означает нарушение схемы.

5. **Установите в проект.** Из корня хранилища сначала план — он ничего не пишет:

   ```
   node "Knowledge-OS/Tools/mv.cjs" adopt
   ```

   План говорит, какой корень проекта и какой режим взят и почему, перечисляет, что в проекте уже есть, и что предлагается изменить. В конце он печатает команду, которой это применить. Режимов два:

   - **`--local` — личная установка** в проект, которым владеет команда. Не меняется ни один отслеживаемый файл: команды и хук ставятся плагином Claude Code `mv` (вызываются как `/mv:check`, `/mv:close`…), точка входа для ассистента — `.claude/rules/memovaleos.md`, а хранилище и файлы бюджета записываются в `.git/info/exclude`. Это режим, который план рекомендует для git-проекта.
   - **`--team` — командная установка**, когда ОС принимают все. Двенадцать команд копируются в `.claude/commands/` (`/mv-check`…), хук — в `.claude/hooks/budget-audit.cjs` и в `.claude/settings.json`, редирект ставится в `CLAUDE.md`, а `.gitignore` получает две строки.

   В клоне этого репозитория, который сам себе проект, план выбирает третий режим, `standalone`: команды ложатся в собственный `.claude/` хранилища, а его `CLAUDE.md` — настоящая точка входа — не трогается.

   Применение — ваш шаг, не ассистента: он пишет в `.claude/` и `.git/`, а это защищённые пути. Для личной установки нужны ещё две команды Claude Code, план печатает их готовыми:

   ```
   node "Knowledge-OS/Tools/mv.cjs" adopt --apply --local
   claude plugin marketplace add "<путь к хранилищу>" --scope local
   claude plugin install mv@memovaleos --scope local
   ```

   Ассистент делает то же самое командой `/mv-adopt`: строит план и передаёт вам команды. Если этот репозиторий склонирован внутрь репозитория проекта, у хранилища свой `.git`, и план попросит указать `--project <корень проекта>` или `--standalone` — так было при первой реальной установке, когда команды ушли внутрь хранилища. Свой `.git` хранилища при личной установке стоит оставить, но без remote этого репозитория: это история знания проекта, а обновления приходят без неё (ниже). Если хранилище лежит не в корне репозитория (пакет монорепо), план попросит `--project` — папку, где вы запускаете Claude.

   При личной установке `CLAUDE.md` команды грузится рядом с хранилищем. Когда его правила разложены в хранилище решениями с `origin: inherited`, `--exclude-host-claude-md` убирает файл из ваших сессий (одна строка `claudeMdExcludes` в `.claude/settings.local.json`); команде и самому файлу это ничего не меняет.

   Язык общения с ассистентом задаёт проект, а не система: `--language ru` (или `en`, `de`…) записывает его в `mvos.config.json` хранилища, а `--notes split` добавляет, что решения и задачи пишутся на этом языке, а архитектура может быть по-английски. Без языка ассистент отвечает на том, на котором пишете вы.

   Каждое применение записывает, что установлено, в `.mvos/install.json` хранилища: корень проекта, режим, файлы с хешами. Проверить установку:

   ```
   node "Knowledge-OS/Tools/mv.cjs" adopt --verify
   ```

   Снять — `adopt --uninstall` (план) и `adopt --uninstall --apply`. Снимается только то, что доказуемо установлено этой системой, и в порядке, который не оставляет проект сломанным; хранилище не удаляется.

   Обновить до новой версии — тоже план, затем применение:

   ```
   node "Knowledge-OS/Tools/mv.cjs" upgrade --from github:GoodJaa/MemoValeOS@os-vN
   node "Knowledge-OS/Tools/mv.cjs" upgrade --from github:GoodJaa/MemoValeOS@os-vN --apply
   ```

   Git-история хранилища для этого не нужна. Файл, который вы не меняли, заменяется новым; ваша правка остаётся; если файл изменили обе стороны, новая версия ложится рядом как `<файл>.mvos-new`. README, `Backlog.md`, `mvos.config.json` и заметки проекта не трогаются. Если после обновления валидатор находит больше ошибок по старым правилам, все файлы возвращаются как были. Копия до os-v6 обновляется скриптом новой версии: `node <новая>/Knowledge-OS/Tools/upgrade.mjs --vault <хранилище> --from <новая> --base github:GoodJaa/MemoValeOS@<текущая>`. Подробности — `Docs/08-Distribution/08-3-Upstream-Sync-and-Upgrade.md`.

   > **Почему это отдельный шаг, а не «уже на месте».** Каноничные исходники лежат в `Knowledge-OS/Dist/` — внутри хранилища, потому что доставка несёт только его. А Claude Code читает команды из `.claude/` в корне проекта или из плагина. Командная установка копирует исходники, и расходиться копиям не даёт правило валидатора `deployed-command-drift`. Личная копий не делает: команды плагина читают текст прямо из хранилища. До версии os-v3 этого шага не существовало, и клон этого репозитория не давал **ни одной** команды.

   Подробности — `Knowledge-OS/Protocols/Deployment-Protocol.md` (его исполняет `/mv-adopt`) и `Docs/08-Distribution/08-2-Adoption.md`.

6. **Что установка не тронет.** Она пишет в дерево, которое ей не принадлежит, и потому ограничена:

   - пишутся только `mv-*`, хук, `.claude/rules/memovaleos.md` и текст между нашими маркерами; всё остальное в `.claude/` принадлежит проекту;
   - `.claude/agents/` и `.claude/settings.local.json` не изменяются вовсе;
   - `settings.json`, который не разбирается как JSON, **не переписывается** — шаг отклоняется с сообщением, файл остаётся байт в байт прежним;
   - удаляется что-то только по `--uninstall`; ничего не индексируется и не коммитится;
   - изменённая копия `mv-*` не затирается и не удаляется без `--yes`.

   Если в корне проекта уже есть свой `CLAUDE.md`, командная установка добавляет редирект сверху в маркерах, прежнее содержимое остаётся на месте, а его **копия** ложится в `Project-OS/Inbox/Adopted CLAUDE.md`. Разложить её по Project OS — отдельная работа с подтверждением по пунктам; инструмент этого не делает, потому что это суждение, а не перенос файла. Личная установка `CLAUDE.md` проекта не трогает.

   > **Не копируйте команды в `~/.claude/commands/`.** Копия видна во всех проектах и расходится с репозиторием при первой же правке, а проектная версия побеждает только в этом проекте. Это не гипотеза: в проекте, где система разрабатывается, пользовательская копия `/mv-close` месяц описывала ритуал из трёх вопросов, которого уже не существовало, и рассогласование обнаружилось только когда её прочитали как авторитетную. Теперь у этого есть поддержанная замена: `adopt.mjs` и `--verify`.

   ```
   /mv-adopt    — установить ОС в проект или снять её (план; применяет владелец)
   /mv-init     — новый проект: Project Initialization Protocol
   /mv-survey [entry-points|budgeted] — существующий репозиторий: Repository Survey Protocol
   /mv-deploy   — развернуть хранилище в Obsidian и подключить MCP
   /mv-resume [<ключ>] [<запрос>] — с чего продолжить: задача этой рабочей копии, следующая
                  свободная или задача по ключу; текст после ключа — запрос на сессию
                  (в т.ч. после разрыва связи с Obsidian)
   /mv-note <что> — записать Finding: дешёвый датированный факт в одну строку (где — связью `affects::`)
   /mv-close    — ритуал закрытия сессии: опись того, что сессия установила, и где это
                  записано, затем Finding; закрытие задачи и эпика, передача работы
                  (Progress задачи, общий Current Context), снимок метрик
   /mv-metrics [флаги context-metrics.mjs] — метрики сессии как есть
   /mv-trend    — тренд по накопленному логу метрик
   /mv-check    — проверка схемы (validate-vault.mjs)
   /mv-sync     — доставить слой ОС в апстрим MemoValeOS
   ```

   В одном хранилище могут работать несколько человек и агентов. Задача считается взятой по своему статусу на любой неслитой ветке, а не по имени человека. Своя задача рабочей копии — локальный курсор вне git, а где остановилась работа, написано в самой задаче. Это работает при любом способе работы с ветками (`Docs/06-Tooling/06-10-Task-Lookup.md`).

### Установка на проект, где уже есть markdown

Валидатор проверяет только то, чем владеет хранилище: `Knowledge-OS/`, `Project-OS/`, `Metrics/`, `Plans/`, `Archive/`, `Docs/` и файлы в корне хранилища. Чужой memory bank, `docs/`, ADR-ы проекта и его `.claude/agents/` не проверяются — их ссылки указывают в граф, которого хранилищу никто не показывал, и считать их битыми было бы неверно.

Раньше это было не так: на установке в проект с собственной базой заметок валидатор выдавал два десятка ошибок, ни одна из которых не была правдой.

Если что-то всё же нужно исключить из обхода — создайте `.mvignore` в корне хранилища, по одному glob-шаблону в строке:

```
legacy-docs/
generated/**
```

Два ограничения намеренные: строка, исключающая слой ОС (`Knowledge-OS/Rules`, `Schema`, `Protocols`, `Tools`), — **ошибка**, а строка, не совпавшая ни с чем, — предупреждение. Число исключённых путей печатается вместе с итогом обхода: исключение, которого не видно в выводе, никто не перепроверяет.

### Подключение ассистента

Плагин MCP Connector поднимает MCP-сервер **внутри процесса Obsidian**. Отсюда главное следствие: **пока Obsidian закрыт, подключения нет**.

Порт и токен доступа плагин показывает в своих настройках; лежат они в `.obsidian/plugins/mcp-tools-istefox/data.json`.

> **Токен — это секрет.** Он даёт полный доступ к хранилищу на запись. Не публикуйте его, не коммитьте и не вставляйте в issue. Файл `data.json` лежит внутри `.obsidian/plugins/`, который исключён из git.

#### Claude Code, Cursor, Cline, Continue

Говорят по HTTP MCP напрямую, никаких мостов не нужно:

```
claude mcp add --transport http obsidian http://127.0.0.1:27200/mcp \
  --header "Authorization: Bearer ВАШ_ТОКЕН"
```

Порт подставьте свой из настроек плагина.

#### Claude Desktop

Нативно HTTP MCP не умеет, нужен мост. Два способа:

- **Бандл.** Экспортируйте `.mcpb` из настроек плагина и откройте его двойным щелчком.

  > **Не используйте чужой `.mcpb`,** в том числе скопированный из чужой копии хранилища. Внутри зашит абсолютный путь к хранилищу, на котором его создавали, — у вас он работать не будет. Экспортируйте свой. Поэтому `obsidian-mcp-connector.mcpb` и указан в `.gitignore`: в репозиторий бандл не попадает.

- **Без бандла** — в `claude_desktop_config.json`:

  ```json
  {
    "mcpServers": {
      "obsidian": {
        "command": "npx",
        "args": ["-y", "mcp-remote", "http://127.0.0.1:27200/mcp",
                 "--header", "Authorization: Bearer ВАШ_ТОКЕН"]
      }
    }
  }
  ```

### Метрики

`validate-vault.mjs` — см. «Установка» выше. Отдельный инструмент — метрики сессии:

```
# Посмотреть, во что обошлась работа ассистента и как он ходил по знанию
node "Knowledge-OS/Tools/context-metrics.mjs"

# То же, с записью строки-снимка в журнал (метка --label обязательна для сравнимых прогонов)
node "Knowledge-OS/Tools/context-metrics.mjs" --write --label <класс>
```

Метрики читают локальные журналы сессий Claude Code и никуда ничего не отправляют. Они разделяют обращения к правилам, к проектному знанию, к коду и к самой системе — и показывают, что ассистент перечитывал.

Одна оговорка о том, чего они не видят: traversal считается по вызовам файловых инструментов. Сессия, которая читает и пишет через `Bash` (`cat`, `sed`), отразится как ноль открытых файлов — при ненулевом числе запросов. Строка в журнале при этом выглядит как данные, хотя данных в ней нет.

Рядом инструменты, отвечающие на соседние вопросы:

```
# Связи: один ли это массив знания или несколько островов
node "Knowledge-OS/Tools/graph-report.mjs"

# Протухание: изменился ли код, на который ссылается заметка, с тех пор как она это утверждала
node "Knowledge-OS/Tools/stale-check.mjs"

# Развёртывание: что стоит в корне проекта и совпадает ли оно с исходниками
node "Knowledge-OS/Tools/adopt.mjs"
node "Knowledge-OS/Tools/adopt.mjs" --verify

# Отдача контекста внешнему инструменту (опционально, см. раздел про провайдер контекста)
node "Knowledge-OS/Tools/context-provider.mjs" --project-root <проект> --vault-root <хранилище>
```

Без `--session <id>` команда берёт последнюю сессию, тронувшую этот vault, — при нескольких параллельных рабочих копиях проекта (например, копия хранилища для контролируемого эксперимента) это может подхватить не ту сессию. Передавайте `--session` явно, если рабочих деревьев больше одного; id ищется по имени файла в `~/.claude/projects/<slug-репозитория>/`.
